## §2 データ準備・書物（book0）構築

### 2-0 共通週次カレンダーと測定窓
- **全脚を金曜終値アンカーの週次グリッドに揃える**（金曜終値確定・PIT。オーバーレイのリバランス基準と一致させる）。
- **book0共通窓** = 3脚（VRP・carry・overlay）の履歴が全て存在する期間の積集合。Deribit DVOLの供給開始（BTC DVOL ≈ 2021年3月）が最も遅いため、共通窓はおおむね **2021年Q2〜直近**（週次250本超）。B実装チームは実データで共通窓の開始週・終了週・本数を確定しレポートに明記すること。
- lab Stage 0のstress窓（BTC週次≤−8%・33週）はこの共通窓に内包される想定。実データで33週前後が再現されることを確認（§4-3）。

### 2-1 VRP脚（週次）
- **長期系列の再構成**: Deribit DVOL日次履歴（`public/get_volatility_index_data`・BTC）から、OBS000037の凍結式で週次コホートVRPリターンを再構成する。
  - vrp_t = DVOL_t − rv_forward_7d_t（rv_forward_7d = [t, t+7]実現ボラ）
  - **net_pnl_pct = (vrp − C_real) × vegaNotionalPct × 100**
  - **凍結パラメータ（変更禁止・OBS000037 meta由来）**: `C_real = 2.8612547352068765`（vol pt/週）、`vegaNotionalPct = 0.00020083800084379173`（f=0.5）。
  - **週次サンプリング**: go-live相当日から7日ごとの**非重複**サンプリング。`is_cohort_anchor=1`の行に相当する週次アンカーのみを1週=1サンプルとして採る。**7日分を合算しない**（Σ全行は約7倍の過大計上になるため厳禁）。
- **フォワードledgerによる整合確認（必須）**: 再構成系列を `research/EXP-OBS000037/10-result/forward/deribit-vrp-forward-ledger-btc.csv` の **`is_cohort_anchor=1` 行の `net_pnl_pct`** と、ライブ重複期間（2026-07-11以降）で突合し、一致（同一式・同一パラメータで再現）を確認する。乖離があれば再構成ロジックの誤りとして是正してから先に進むこと。
- **禁止**: CoinMetrics・Bybit/OKX・Deribit以外のオプションベンダー・有償ベンダーからのVRP/IV取得。Deribit公開APIのみ。

### 2-2 キャリー脚（週次）— 基差MTMの扱い（本Stageの核心）
- **基差MTMは既にOBS000032実データに内在する**。以下を使い分ける:
  - **長期stress系列（§4のmaxDD/CVaR算出母体）**: `research/EXP-OBS000032/10-result/daily-pnl-{btcusdt,ethusdt}-*.csv` を用いる。
    - 列: `date, spot_return_bps, perp_return_bps, funding_pnl_bps, basis_pnl_bps, total_pnl_bps`。
    - **`basis_pnl_bps` が基差MTM項**であり、lab近似に欠けていた成分。日次キャリー純益 = `total_pnl_bps`（funding＋基差MTM＋現物/perp＋コストを内包）を採用する。**funding_pnl_bpsのみの使用は禁止**（lab近似の再現になり本Stageの目的を無に帰す）。
    - T1/T2/T3/calmは会計・レジーム区分の断片である可能性があるため、**B実装チームは連続したフル期間日次系列を1本に再構成**し、行数がbootstrap参照（BTC≈2493日／ETH≈2413日、OBS000032 forward-interim-metrics.json由来）と整合することをsanity anchorとして確認すること。断片の重複・欠落・二重計上がないこと。
  - **ライブ重複期間の整合確認**: `forward/forward-paper-ledger-{btc,eth}.csv` の `sleeve_daily_return_pct`（=基差MTM込みの実現日次リターン。`daily_net_pnl_bps` は `perp_short_mtm_bps`＋`funding_flow_bps`＋`spot_leg_pnl_bps`＋各コストを内包し基差MTMを含む）と、長期系列の同一日を突合し会計整合を確認する。
- **週次集計方法**: 日次リターンを金曜アンカー週（金曜終値→翌金曜終値）で束ね、週内日次の複利で週次リターンとする（週次リターン = Π(1 + r_daily) − 1、r_daily = `total_pnl_bps`/10000 または `sleeve_daily_return_pct`/100）。**週の切り口は金曜終値**でVRP・overlayと統一する（曜日不一致による見かけ上の相関劣化を避ける）。
- **清算・追証の織り込み**: OBS000032会計（方式I・分離証拠金・清算損二重計上なし・perp floor(0)頭打ち・reversal 4脚コスト24.064/24.224bps）を**そのまま踏襲**。新会計を発明しない。清算/追証発生日は週次系列に損失として自然に反映される。

### 2-3 タイムアライメント（VRP帰属タイミングの1週オフセット処理）
- VRPは vrp_t = DVOL_t − rv_forward_7d であり、**アンカー日tに開いたポジションが [t, t+7] で実現**する forward-looking 損益。一方 carry/overlay の週次リターンは当該週 [t, t+7] の実現損益。
- **整合規約（固定）**: VRPコホートアンカーtの `net_pnl_pct` を、**その forward実現窓 [t, t+7] が属する週バケット**に割り当てる（観測日tではなく実現窓基準）。これでcarry/overlayの [t, t+7] 実現リターンと同一週バケットに揃う。
- **残差オフセットの感度検査（必須・報告のみ）**: 上記整合に対し VRP系列を **±1週シフト**した場合の §4 指標を副次出力する。主判定（§7）は整合規約（0シフト）で行い、±1週シフトは頑健性の参考情報とする（判定基準には用いない＝HARKing防止）。

### 2-4 book0の構成（事前登録・変更不可）
- **book0 = VRP脚 と carry脚 の結合**（overlay抜き）。
- **内部配分（主定義・凍結）**: VRP・carryを**逆ボラティリティ加重（＝両脚のリスク寄与を等分）**で結合し、結合後に **book0全体を年率実現ボラ10%へスケール**する（overlayも年率10%vol-target前提のため、a≈0.4201が overlay リスク寄与15%を与える前提条件を満たす）。
- **副次定義（報告のみ・判定に使わない）**: 資本比 60/40・40/60（VRP/carry）でも §4 指標を出力し頑健性を示す。主判定は逆ボラ加重（等リスク寄与）1本で確定する。
- vol推定は**過去実現ボラ・shift済（先読み禁止）**。週次系列上でのローリング窓（例: 過去52週）で推定し、当該週より前の情報のみ使用すること。

## §3 オーバーレイ（TSMOMシグナル）実装設計

### 3-1 BTC/ETH週次リターンの取得
- **Binance S3（data.binance.vision）** の spot 日足（BTC/USDT・ETH/USDT）を使用。金曜終値で週次グリッド化。
- **禁止**: 有償ベンダー・CoinMetrics等。Binance S3公開データのみ。

### 3-2 TSMOMシグナル（3ルックバック平均・事前登録・変更不可）
- ルックバックは**暦日ベース**（30/60/90日）で価格差の符号を取り平均する:
```
# P: 日次終値系列（金曜アンカー・PIT）
def tsmom_signal(P, t):
    s = 0.0
    for L in (30, 60, 90):           # 暦日
        s += sign(P[t] - P[t - L])   # +1 / 0 / -1
    return s / 3.0                    # ∈ [-1, +1]
# 資産i（BTC, ETH）ごとに独立算出。t=金曜終値確定日、翌営業日適用（PIT）。
```
- シグナルは金曜終値で確定、**翌営業日から週次ポジションに適用**（先読み禁止）。

### 3-3 vol-targetサイジング（過去60営業日σ・shift済）
```
# 年率10%vol-target。σは過去60営業日実現ボラ（当該日を含まない・shift済）
sigma_daily = std(daily_returns[t-60 : t])          # tを含まない
sigma_annual = sigma_daily * sqrt(365)              # 暗号は365日換算
w_i = signal_i * (0.10 / sigma_annual)              # 資産iの目標エクスポージャ
# 週次リバランス時に w_i を適用。σは必ずshift済（先読み禁止）。
```
- **執行コスト 0.10%/片道**を週次リバランスのターンオーバーに課す。
- BTC・ETHの2脚を合算してオーバーレイ・スリーブ週次リターンを得る（2銘柄均等）。

### 3-4 リスク寄与配分 a≈0.4201 の実装
- **a = √(0.15/0.85) ≈ 0.4201**（overlay分散リスク寄与15%・凍結値）。
- book1 = book0（年率10%vol化済）+ a × overlay（年率10%vol-target済）。両脚が同一目標ボラ・低相関前提で overlay リスク寄与 = a²/(1+a²) = 0.15、実達成rc=0.15。
- 実達成リスク寄与を副次出力で確認（想定15%から大きく乖離しないこと。乖離が大きい場合は前提破れとしてレポートに明記。判定閾値の変更はしない）。

### 3-5 予測単位テスト（overlayヘッジ性の単体命題・必須）
- stress窓（§4-3で確定するBTC週次≤−8%窓）での **条件付き相関** を算出:
  - ρ(overlay, VRP) … Stage 0の−0.331近傍の負を再現するか
  - ρ(overlay, carry_basisMTM) … §5で詳述
- **BTC選定 / ETH確認の分解**（過学習炙り出し）: overlay脚をBTC寄与・ETH寄与に分け、条件付き相関の符号が**両資産で独立に負方向**を保つか確認する（片側資産のアーティファクトでないこと）。これがStage 1における選定(BTC)/確認(ETH)プロトコルの実体。全パラメータは凍結済みのため新規フィットは無い＝本Stageは実質confirmation runである点を明記する。

## §4 G-ensemble 判定（Stage 1キルゲート）

### 4-1 book1の構築
- book1 = book0 + a × overlay（a≈0.4201・§3-4）。共通窓（§2-0）の週次系列で構築。

### 4-2 テールリスク指標（算出定義・固定）
- **maxDD**: 週次リターンの複利累積エクイティ曲線からのピーク→トラフ最大下落率（book0・book1それぞれ）。
- **CVaR95**: 週次リターン分布の下位5%の平均（＝95% Expected Shortfall。符号は損失を正で扱うか損益で扱うか、B実装は明示。改善＝テール損失の縮小方向）。
- 両指標を book0（overlay無）と book1（overlay有）で算出し、改善率 = 1 − |指標(book1)| / |指標(book0)|。

### 4-3 stress窓での条件付き相関確認（G-tail再現）
- 共通窓上で **BTC週次リターン ≤ −8%** の週を data-driven に抽出（lab: 33週）。抽出週数をレポートに明記。
- 当該stress窓で ρ(overlay, VRP)・ρ(overlay, carry_basisMTM) を算出し、Stage 0（−0.331 / −0.238）と整合方向（負）を確認。

### 4-4 成功基準（変更不可・事前固定 — §7に再掲）
- **maxDD(book1) ≤ maxDD(book0) × 0.90**（maxDD 10%以上改善）**かつ**
- **CVaR95(book1) ≤ CVaR95(book0) × 0.90**（CVaR95 10%以上改善）
- 両方を**同時に**満たした場合のみ PASS。

### 4-5 失敗判定
- maxDD改善・CVaR95改善の**いずれか一方でも10%未達**なら **STOP（系統廃棄）**。
- STOP時も §3-5/§5 の条件付き相関と単体指標は必ず出力し、廃棄理由（ヘッジ性が無いのか／ヘッジ性はあるが規模不足なのか）を切り分けてレポートに残す（負の結果もPJ000001資産）。

## §5 carry脚テール独立の追加検証

### 5-1 Stage 0でbootstrap CIがゼロを跨いだ理由の考察（必須記載）
- Stage 0: ρ(carry)=−0.238だが block-bootstrap で frac_le0=0.89・CIがゼロ跨ぎ＝**符号の頑健性が弱かった**。
- 主因候補: (a) lab carryが基差MTM欠如の近似でテール挙動が過小/歪曲、(b) stress週数（33週）が少なくbootstrapの検出力不足。本Stageは(a)を基差MTM込みで是正し、(b)は検出力限界として明示する。

### 5-2 基差MTM込みcarryでの非正相関確認
- §2-2の基差MTM込み週次carry系列で、stress窓の条件付き相関 ρ(carry_basisMTM, overlay) と **block-bootstrap CI**（blockLen=7・N=5000・seed固定）を算出。
- **ガードレール基準（副次・エスカレーション用）**: 点推定 **ρ(carry_basisMTM, overlay) ≤ 0**（非正）であること。CIのゼロ跨ぎは検出力限界として許容する（stress週数が少ないため）。
- **本Stageの数値PASS/STOP判定は §4/§7 のmaxDD・CVaR95のみで確定する**。本§5はそれを補強・解釈する診断であり、単独でPASSを与えない。

### 5-3 失敗時の判断フロー
- ρ(carry_basisMTM, overlay) の点推定が **正（>0）**に転じた場合: §4がPASSでも**自動採用しない**。C品質チーム・戦略チームへ**エスカレーション**（共有テール打ち消しの機序が崩れる兆候のため、司令塔判断を仰ぐ）。レポート冒頭に赤字警告を明記。
- ρが非正（≤0）で §4 PASS: 通常どおりC品質チームへ採用候補として送る。

## §6 既知の弱点（Known Limitation・変更不可・レポート必須記載）
以下は出力レポートに**必ず注記**すること（採用時も本番運用の前提制約として引き継ぐ）:
1. **速いV字gapは非ヘッジ**（FTX/SVB型・数日で急落急反発）。本オーバーレイ（遅い下落専用のslow-trend捕捉）では補えない。この型の共有テールは別手段（例: 明示的オプションテールヘッジ）を要する — 本系統の守備範囲外。
2. **carry脚テール独立の不確実性**（§5-1のbootstrap CIゼロ跨ぎ問題）。基差MTM込みで再検証するが、stress週数の少なさから符号の統計的頑健性には限界が残る。
3. **フォワード実データが短い**（VRP live 11日・carry live 18日・2026-07時点）。§4の長期stress判定は**バックテスト再構成系列**が母体であり、フォワード整合はライブ重複期間の会計突合（§2-1/§2-2）に限定される。フォワード蓄積継続による将来再確認が必要。
