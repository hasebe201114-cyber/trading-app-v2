## 0. この実験の性質（最重要・冒頭明記）

**Stage 0 は「シグナルの良し悪し」を一切判定しない。** 横断モメンタムや横断Fundingキャリーにエッジがあるか（IC・Sharpe・hitRate等）は**Stage 1以降で測る**ものであり、本Stage 0では**測定も言及もしない**。

Stage 0 が答える問いはただ一つ:
> **「サバイバーシップ・バイアスを排したpoint-in-time（PIT）の上位N（N=20〜50）ユニバース＋日足OHLCV＋Funding履歴を、Bitget USDT-perpで実運用可能な品質・期間で実際に組めるか」**——純粋な**データ調達・基盤構築の技術的成立性**の調査。

理由（prescreen 4項の帰結）: レビューのストップ条件「サバイバーシップを含めない横断バックテストの結果は、どれだけ良くても採用しない」。ゆえにデータ実現可能性は「あれば良い」ではなく**Stage 1以降の全検証の前提条件**であり、ここが立たなければどんな好結果も偽陽性製造機になる。だから最初に単独ゲートとして安く潰す。

**判定（go/no-go・分岐）はC懐疑検証官が行う。** B検証実装官は**事実・実測値・生ログのみ**を報告し、判定語（達成/未達/十分/不十分/go/no-go/組める/組めない 等）を使わない（後述「B実装官への指示」）。

## 1. 対象ユニバースの定義（N＝対象銘柄数の決め方・固定）

### 1-1. 流動性ランキングのソースとスナップショット
- **母集団**: Bitget mix market の **USDT建て無期限先物（USDT-FUTURES／USDT-perp）全銘柄**。
- **流動性指標**: 各銘柄の **直近24時間のUSDT建て出来高（quote volume / usdtVolume 相当）** を採用（板の厚みでなく出来高を一次指標とする）。B実装官は tickers エンドポイントが返す出来高フィールドの**正確な名称と単位（USDT建てか、コイン建てか）を実測で確認**し、USDT建てに正規化した値でランク付けすること。
- **スナップショット時点**: Stage 0 実行時に **1回だけ**、全USDT-perpの24hティッカーを取得し、その**取得UTCタイムスタンプを記録**して固定スナップショットとする（複数回取得して都合よく選ばない）。このスナップショットは「**現時点**での流動性ランク」であり、後述G0-3のPIT（過去時点のas-ofランク）とは役割が異なる点に留意。
- **ランキング**: 24h USDT出来高の降順。同点・データ欠損銘柄の扱い（除外/最下位）は実装で固定し、生ログに残す。

### 1-2. N の扱い（Stage 0では固定値に絞らず「帯」で報告させる）
- Stage 0 は**上位50までを対象に取得を試み**、**N=20 / N=30 / N=50 の3ティア**それぞれについてカバレッジ（下記G0-1〜G0-3の各実測値）を報告させる。
- **Stage 1以降で使う確定Nは Stage 0 の実測を踏まえて別途固定する**（＝Stage 0でNを1点に決め打たない。深さ・死銘柄カバレッジの実態を見てから決める設計）。ただし本spec上の**合否判定の主軸は N=30 ティア**（上位30＝横断LS上位下位で十分なブレッドが立つ現実的中庸）に置く。N=20は最小ブレッドの下限確認、N=50は上限側の履歴薄さ確認用。

## 2. Stage 0 の合否ゲート（G0-1〜G0-3・回す前に基準を固定）

各ゲートについて「**達成 / 部分達成 / 未達**」の境界を数値・基準で定義する。**判定はCが下す**。B実装官は各基準に対応する**実測値・生データを揃えるだけ**。

### G0-1: 現在上場中の上位N銘柄の履歴深度（日足OHLCV＋Funding）

**測定対象**: 上位50各銘柄について、日足OHLCVの最古日・本数・欠損日数、Funding履歴の最古日・イベント数・欠損を実測。

**期間の深さの基準線（本日=2026-07-05を起点に固定）**:
- **3年ライン = 2022-07-05以前**から連続取得できるか（prescreen「最低3年」を厳密日付化）。
- 参考ティアとして **4年ライン=2021-07-05以前**、**6年ライン=2020-07-05以前** も各銘柄で判定・報告。
- **レジーム被覆の必須確認**: **2022年通年（2022-01-01〜2022-12-31＝BTC弱気・総崩れレジーム）** を日足・Fundingともにカバーするか（複数レジーム＝弱気を含むかの核心）。
- 「連続」の定義: 期間内の**欠損日が総営業日数の5%未満**（日足）。Funding欠損も併記。

**合否基準（主軸 N=30 ティアで判定）**:
- **達成**: 上位50のうち、日足OHLCV＋Funding**両系列**が3年ライン（2022-07-05以前）から欠損5%未満で連続取得できる銘柄が **30本以上**、**かつ**そのうち**2022年通年**をカバーする銘柄が **20本以上**。
- **部分達成**: 上記の3年連続取得銘柄が **20〜29本**、または2022通年カバーが **10〜19本**。横断LSは最小限組めるが、ブレッドまたはレジーム深度が想定を下回る。
- **未達**: 3年連続取得銘柄が **20本未満**、または2022通年カバーが **10本未満**（＝横断分散が原理的に効く最小ブレッドに届かない）。

**あわせて実測・報告させる（Cの判断材料）**:
- history-candles / history-fund-rate の**ページング上限**（1リクエストの最大件数、endTime/pageNo等での遡及可能な最深時点、総深度の実測）。
- 上位銘柄でも履歴が浅い（例: 上場が新しい）銘柄がどの程度あるかの分布。

### G0-2: 上場廃止・消滅した銘柄の再構成可否（サバイバーシップ排除の可否）

**これがStage 0最大の争点**（prescreen 3項）。Bitget公開APIは原則現行上場契約のみを返す設計の見込みで、Binanceの `data.binance.vision` に相当する公開バルクアーカイブも知られていない＝サバイバーシップ対応はBinance以上に難しい可能性がある。以下を**この順で**調査。

**調査手順（B実装官が実施）**:
1. **contractsエンドポイントの精査**: `contracts`（USDT-FUTURES）が返す全フィールドを記録。**status/symbolStatus等で「上場廃止・決済済み」を示す値や、過去シンボルが含まれるか**を確認。現行のみなら「現行のみ」と事実を記録。
2. **公開APIでの死銘柄履歴の直接取得テスト**: **実在した廃止シンボルを最低3件特定**し（B実装官が外部情報・過去のBitget上場一覧等から同定。同定手段も記録）、それらのシンボルで history-candles / history-fund-rate を叩き、**現行contractsに無いシンボルでも過去データが返るか**を実測（返る/エラー/空、レスポンス原文を残す）。
3. **Bitgetの他の公開手段の探索**: productTypeの他値・アナウンス/お知らせAPI・決済済み契約一覧の有無など、公開範囲で死銘柄情報に到達できる経路がないかを調査（あれば実URL・スキーマを記録）。
4. **外部無料ソースでの再構成可否調査（範囲を限定）**: 上記1〜3で公開APIから取れない場合に限り、以下を**「実現可能性の調査＋最小実証」に限定**して行う（**完全な台帳の構築はStage 0のスコープ外**）:
   - CoinGecko / CoinMarketCap 等の無料APIで、**Bitget perpに過去上場していた銘柄のシンボル・上場/廃止日・当時の概略流動性**が引けるか。
   - Bitgetの上場廃止アナウンス/サポートページが**機械的に取得・解析可能な形か**（HTMLスクレイプの現実性含む）。
   - 上記で、特定済みの廃止シンボル**3件について、上場期間と当時の流動性ランク（概略）を再構成する手段が実在するか**を実例で示す（3件の再構成サンプルを提示。完全網羅性は未検証でよい）。
5. **サバイバーシップ規模の見積り材料**: 現行上場USDT-perp銘柄数と、（判明する範囲で）過去に上場廃止された銘柄の**概数**を報告し、Cが「死銘柄を除外した場合のバイアスの向き（生存銘柄のみ＝上振れ）と規模」を見積れる材料を揃える。

**合否基準**:
- **達成**: Bitget公開APIから、廃止銘柄の日足＋Funding履歴が安定取得できる（現行contractsに無いシンボルでも history系が過去データを返す）ことを、**実在の廃止シンボル3件以上で実証**。
- **部分達成**: 公開APIでは死銘柄を直接取れないが、**外部無料ソース＋Bitgetアナウンス等から、廃止銘柄のシンボル・上場/廃止日・当時の概略流動性ランクを機械的に再構成する現実的手段が実在する**ことを、**3件の実例**で示せる（完全網羅性は未検証でよい）。
- **未達**: 公開APIでも無料外部ソースでも、廃止銘柄の存在期間・当時の流動性ランクを再現する手段が見つからない（＝サバイバーシップ排除が無料手段では不可能）。

### G0-3: point-in-time（PIT）ユニバース定義の機械的再現性（先読み排除）

**測定対象**: 各リバランス日の「その時点で実在した銘柄」だけで流動性ランク上位Nを付ける定義が、**先読みなく・機械的に再現可能**な形で構築できるか。**小規模プロトタイプで実証**させる。

**プロトタイプの範囲（固定）**:
- 期間: **直近1年（2025-07-05〜2026-07-05）**に限定（PIT機構の実証が目的。全期間の本構築はStage 1以降）。
- リバランス頻度: **月次（各月初）** を既定（②系のHORIZON=10日でもよいが、Stage 0の機構実証は月次で十分。採用頻度はStage 1で確定）。
- as-ofランキング: 各リバランス日 `t` において、**`t` までに取得可能なデータのみ**（例: 直近30日の平均USDT出来高）で上位Nを選定。`t` 時点で日足が存在する（＝当時上場していた）銘柄のみを母集団とする。

**実証すべき性質（プロトタイプ出力で確認）**:
1. **再現性**: 同じ入力で二度実行し、各リバランス日のユニバースが**完全一致**する（決定的）。
2. **先読み排除**: as-ofランキングに**未来情報が混入しない**こと（`t` 時点で未取得の将来出来高・将来の上場/廃止を参照しない）をコード構造とサンプル出力（各月のユニバース一覧）で確認できる。
3. **銘柄ライフサイクルの組込み可否**: G0-2で死銘柄データが得られる前提なら、**「上場していた期間だけユニバースに含め、廃止後は自動除外」するロジックが実装可能**であることをコードで示す（データが未取得でも**ロジック骨格＋合成データでの動作**を提示可）。死銘柄データが得られない場合は、その旨と「現行銘柄限定のPITしか今は組めない」ことを事実として記録。

**合否基準**:
- **達成**: 直近1年で、各リバランス日ごとに「その日までのデータのみ」で上位Nを構築するプロトタイプが動作し、**(1)再現性・(2)先読み排除**を出力で確認でき、**(3)死銘柄の出入りをユニバース定義に組み込む機構が（実データまたは合成データで）実装可能**であることをコードで示せる。
- **部分達成**: (1)(2) は現行銘柄で満たすが、(3) の死銘柄組込み機構が **G0-2のデータ制約で実データ実証できない**（生存銘柄限定のPITは組めるが、真のサバイバーシップ排除PITは未実証）。
- **未達**: 各リバランス日のas-ofランキングが**機械的・再現的に構築できない**（データ構造・API制約でPIT定義が原理的に不可能）。

## 6. 選定/確認・多重検定に関する注記（Stage 0の性質に合わせて）

- Stage 0 は**シグナル検証ではない**ため、選定/確認データ分割（過学習の炙り出し）による signal 判定は行わない。ただし **G0-3のPITプロトタイプは、Stage 1以降で「held-out銘柄OOS」（Cが求めてきた検証武器）を成立させるための土台**である。よってPIT定義は**先読み排除を厳格に**実装し、Stage 1で銘柄を選定/確認群に分ける自由度を確保できる形にすること。
- Stage 0 で**シグナルのパラメータ（ルックバック・閾値・N・リバランス頻度等）を探索・最適化してはならない**。Nの帯（20/30/50）報告・月次リバランスは「データが組めるか」の技術確認であって、成績を見て選ぶ対象ではない。確定値はStage 1のspecで事前登録する。
