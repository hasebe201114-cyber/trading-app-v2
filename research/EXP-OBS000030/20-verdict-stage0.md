## 中核結論（90日頭打ちの切り分け）

**「全50銘柄が約90日で頭打ち」は Bitget公開APIの真の制約ではなく、B実装官の取得スクリプト `scripts/fetch-bitget-data.ts` のページング・バグである。** C自身がBitget公開APIを独立に叩いた結果、**日足OHLCVは少なくとも2019年まで遡って取得可能**であることを実証した（後述）。B実装官のG0-1の見出し「3年ラインカバー=0本/50」は**偽陰性**であり、真実は「BTC・ETH等の主力銘柄は7年弱の日足履歴を持ち、3年ライン・2022通年を余裕でカバーする」。

一方、**Funding履歴（history-fund-rate）は約90日で頭打ちが真の制約**であることも独立に確認した（バグ修正後も深くならない別種の問題）。この2点は原因が異なるため分けて扱う。

## バグの特定（`scripts/fetch-bitget-data.ts`）

### 主因バグ（日足が90日で止まる直接原因）— L211
```ts
if (candles.length < pageSize) {          // pageSize=200
  log(`... reached pagination limit ...`);
  break;                                   // ← 90 < 200 なので毎回ここで即break
}
```
Bitget の `history-candles` は **1D では1リクエスト最大約90本**しか返さない（limit=200を指定しても90でキャップ）。`length < limit` を「履歴の終端」と誤解したため、**1ページ目で必ずループを抜け**、後方遡及が一度も走らなかった。全50銘柄が判で押したように90日で揃ったのはこのため（データの性質ではなく制御構造の産物）。

### 副次バグ（仮に主因を直しても遡及が壊れる）— L206-207
```ts
const oldestTimestamp = parseInt(candles[candles.length - 1][0]); // ← 実際は「最新」
endTime = oldestTimestamp - 1;
```
Bitget は日足を**昇順（古い→新しい）**で返す（保存済み `history-btcusdt.json` の先頭=2026-04-04, 末尾=2026-07-02 で確認）。よって `candles[length-1]` は**最古ではなく最新**。ログの「最古 2026-07-02」表記はこの取り違えの証拠。正しくは `Math.min(...timestamps)`（＝昇順なら `candles[0]`）を次ページの `endTime` に使う。

### 同型バグ（Funding）— L282
```ts
const pageSize = 500;                      // Bitget実上限は100（超過分は黙ってキャップ）
...
if (fundRates.length < pageSize) break;    // 100 < 500 で毎回1ページ目でbreak
```
Bが各銘柄で「funding 100件」で止まったのはこのため。正しくは `pageSize=100` で `pageNo` を進める。**ただし修正しても総深度は約270件（≒90日）で枯渇**（検証3）＝これはバグではなく真の制約。

## 判定理由（差し戻しの根拠＝負の結果の資産化）

1. **偽陰性の罠（今回の該当罠）**: Stage 0の主軸ゲートG0-1の「0本/50」は、Bitgetの真の制約ではなく取得スクリプトの制御構造バグの産物。この値のまま**分岐(a)保留や(b)探索限定を宣告すれば、実際には7年の日足が取れる土俵を「データが組めない」と誤って封印**することになり、過去の偽陽性と対をなす**偽陽性製造機の裏返し（安価に潰すはずのゲートで誤って有望土俵を殺す）**に陥る。Cの役目は好結果の棄却だけでなく、悪い結果の鵜呑み阻止でもある（オーケストレーター明示指示）。
2. **G0-3の出力もG0-1バグに連鎖汚染**（同じ candles を入力にするため「2026-04まで全月ユニバース0件」は当然の帰結）。よって G0-3 も再実行対象。
3. **G0-2は結論の向きは支持されるが証拠が脆弱**（架空シンボルをテスト）。真の廃止銘柄（40309）での再取得と、40309コードを死銘柄検出の部分的シグナルとして使えるかの追検証が必要。

## 差し戻し内容（B検証実装官への具体指示）

**差し戻し先: B検証実装官**（A設計官の spec 変更は不要＝基準は妥当、実装のみ修正）

### 必須修正（`scripts/fetch-bitget-data.ts`）
1. **history-candles の後方ページング修正**:
   - 終了条件を `candles.length < limit` から **`candles.length === 0`（空応答＝終端）または「最古タイムスタンプが前ページから前進しない」** に変更。
   - `endTime` カーソルは **昇順前提で `Math.min(...timestamps) - 1`**（≒`candles[0]` のts−1）を使用。取り違えを解消。
   - 1D は1リクエスト約90本上限を前提に、目標起点（例: 2019年 or spec下限2022-07-05）まで**複数ページ遡及**。BTCで約29ページの実績。
2. **history-fund-rate の修正**: `pageSize=100`（上限）に是正し `pageNo` を進める。**その上で真の深度（BTCで≒270件/≒90日で枯渇）を事実として計測・報告**。日足と非対称な浅さである点を明示。
3. **G0-2 の再取得**: テスト銘柄を**実在した廃止銘柄**に差し替える（SRMUSDT など、`history-candles` が **code 40309 "removed"** を返すものを死銘柄として同定）。`40034`（不存在）と `40309`（廃止済）の**コード識別を実装**し、廃止銘柄で candles/funding 本体が返るか否かを再検証。40309 を「かつて上場した銘柄」検出の部分手段として使えるかも所見化。
4. **G0-3 の再実行**: 修正後の深い candles を入力に、直近1年PITプロトタイプを再走。ユニバースが各月で実際に構成されるかを再測定。

### 再測定後にCが判定できるよう出力してほしい値
- 上位50各銘柄の**修正後**の日足最古日・本数・欠損%、3年/4年/6年ライン・2022通年カバー（N=20/30/50ティア別集計）。
- Funding の**真の最深時点**（各銘柄、≒90日で枯れる想定の裏取り）と、日足との深度差の一覧。
- 死銘柄再取得結果（40309銘柄リスト・本体データ可否）。

## 再測定後に見えてくる論点（Cからの予告・Sと司令塔向けの前倒し所見）

差し戻し後の再測定は、おそらく次の**非対称な構図**を露呈する（Cの独立検証からの予測。判定は再測定後に確定する）:
- **日足OHLCV = 深い（7年）** → Stage 1（横断**モメンタム**）のデータ土俵はBitget公開APIだけで成立する見込みが高い。G0-1の日足レグは達成側へ動く可能性大。
- **Funding履歴 = 浅い（≒90日）** → Stage 2（横断**Fundingキャリー**）は公開APIだけでは3年深度を満たせない公算。G0-1のFundingレグは未達側になり得る。
- **死銘柄の履歴本体 = 公開APIでは取得不可**（40309でも本体データは返らない）→ サバイバーシップ排除は公開APIのみでは依然として立たず、**分岐(a)/(b)の論点はG0-2側に残る**。

→ 従って再測定後の最終判定は「**日足モメンタムなら土俵が立つが、Fundingキャリーと完全なサバイバーシップ排除は無料手段では制約が残る**」という**スリーブ別・段階別の切り分け**になる可能性が高い。これはStage 1（モメンタム）を先行させるという参謀官の元設計と整合的。ただし**現時点では宣告せず**、Bの再測定の生値を待つ。
