## 0. この実験の性質（最重要・冒頭明記）

**Stage 0 は「シグナルの良し悪し」を一切判定しない。** 短時間足の平均回帰・清算反発・モメンタム縮小にエッジがあるか（IC・Sharpe・hitRate等）は**Stage 1以降で測る**ものであり、本Stage 0では**測定も言及もしない**。

Stage 0 が答える問いはただ二つ:
> **(問1) Bitget USDT-perp で、4h/1h/15m の短時間足OHLCVを「2022弱気を含む複数年の深度」で、実運用可能な品質・連続性で実際に取れるか。**
> **(問2) 高頻度戦略の生死を分ける執行コスト（テイカー/メイカー手数料・実効スプレッド・板厚由来スリッページ）を、Bitget実値で往復コストモデルに落とせるか。**

——純粋な**データ調達・執行コストモデル化の技術的成立性**の調査。シグナル検証ではない。

理由（prescreen「データ実現可能性の厳格評価」の帰結）: 短時間足は日足よりさらに履歴が浅い公算が高く（030で日足7年／Funding90日という粒度依存の非対称が実測された）、2022弱気に届かなければレジーム盲検で検証が成立しない。また高頻度はネットコスト後が主ゲートであり（prescreen必須条件③）、執行コストがモデル化できなければどんな好結果も偽陽性製造機になる。だから最初に単独ゲートとして安く潰す。

**判定（達成/部分達成/未達・分岐）はC品質チームが行う。** B実装チームは**事実・実測値・生ログのみ**を報告し、判定語（達成/未達/十分/不十分/go/no-go/取れる/取れない/問題ない/難しい 等）を使わない（後述「7. B実装官への指示」）。

## 1. 対象銘柄の定義（固定）

### 1-1. 対象銘柄＝BTCUSDT・ETHUSDT の2銘柄に固定
- prescreen推奨（単一資産中心・BTC/ETH中心）に従い、**`BTCUSDT` と `ETHUSDT`（Bitget USDT-FUTURES / USDT-perp）の2銘柄**を全ゲート（G0-1/G0-2/G0-3）の対象とする。

## 2. Stage 0 の合否ゲート（G0-1〜G0-3・回す前に基準を固定）

各ゲートについて「**達成 / 部分達成 / 未達**」の境界を数値・基準で定義する。**判定はCが下す**。B実装官は各基準に対応する**実測値・生データを揃えるだけ**。

基準日（アンカー）: **本日 = 2026-07-05（UTC）** を起点に固定。

### G0-1: 短時間足OHLCVの履歴深度（4h / 1h / 15m）

**測定対象**: BTCUSDT・ETHUSDT の各粒度（4h / 1h / 15m）について、`history-candles` を**空応答になるまでページング**し、以下を実測:
- 最古足のUTCタイムスタンプ（＝実遡及の最深時点）。
- 総取得本数。
- 実遡及年数（本日 − 最古足）。
- 2022年内の欠損本数（後述の期待本数に対する欠損率）。

**「2022通年カバー」の厳密定義（数値化）**:
- **2022通年 = 2022-01-01 00:00:00 UTC 〜 2022-12-31 23:59:59 UTC**。
- カバー成立の条件: 当該粒度の**最古足が 2022-01-01 00:00 UTC 以前**（＝2022年初より前から連続して存在）**かつ** 2022年区間の**欠損率 < 5%**。
- 2022年の期待本数（欠損率の分母。365日で計算）:
  - **4h**: 6本/日 × 365 = **2,190本**
  - **1h**: 24本/日 × 365 = **8,760本**
  - **15m**: 96本/日 × 365 = **35,040本**
  - （B実装官は実カレンダーで厳密本数を再計算してよい。欠損＝連続タイムスタンプ列の抜けとして定義し、欠損本数・欠損率を実測値として報告する。）
- 参考ティア（各粒度・各銘柄で併記）: **3年ライン = 2022-07-05 以前**、**4年ライン = 2021-07-05 以前** から連続取得できるかも判定・報告（2022以前にどこまで遡れるかの分布を残す）。

**合否基準（判定はC。BTC・ETH両方で評価）**:
- **達成**: 4h / 1h / 15m の**少なくとも1粒度**が、BTC・ETH**両銘柄**で「2022通年カバー（最古足 ≤ 2022-01-01・欠損率 < 5%）」を満たす。＝2022弱気レジームを含む複数年の短時間足土俵が無料APIで立つ。**達成の場合、Cは2022に到達した最短粒度（=最も高頻度な粒度）を Stage 1 の確定粒度候補として特定する材料を得る。**
- **部分達成**: 粗い粒度（例: 4h）は2022通年カバーを満たすが、細かい粒度（1h/15m）は2022に届かない。または BTC は満たすが ETH は満たさない（銘柄非対称）。＝頻度の上限が制約されるが、レジームを含む検証は一部粒度で成立し得る。
- **未達**: 4h / 1h / 15m の**全粒度**が2022通年カバーを満たさない（全粒度で最古足が2022-01-01より後）。＝短時間足がレジーム盲検になり検証不成立。

**⚠ 030 Stage0で発生した3重ページングバグ — 絶対に再発させないこと（B実装官への必須チェックリスト）**

030 Stage0では `fetch-bitget-data.ts` の history-candles / history-fund-rate ページングに3つのバグがあり、「日足3年カバー0本」という**偽陰性**を生んだ（C独立再現で「真は日足7年・BTC 2019-07起点」と判明・差し戻し）。短時間足は日足よりページ数が桁で増える（4h/1h/15mは同一期間で6/24/96倍のページ）ため、**同じバグが出れば深度を大幅に過小評価する**。以下3点を実装前に固定し、生ログで自己点検すること:

1. **【終了条件の誤り】ページング終了は「空応答（返却0件）」のみで判定する。**「返却件数 < limit で終了（`length < limit → break`）」は**禁止**。理由: Bitgetは `limit` を指定しても**粒度・時間帯によって実際の返却件数が limit に満たないことがある**（030では1D=90本キャップに毎回1ページ目で当たり打ち切られた）。`limit` 未満の返却を「もう履歴が無い」と誤読してはならない。**「返却0件（空配列）になるまで遡り続ける」を終了条件にする。**
2. **【昇順/降順の取り違え】endTime カーソルは、直前ページの返却データの"最古"タイムスタンプに正しく更新する。** 過去へ遡るページングでは、次ページの `endTime` に**そのページで返ってきた最古足のタイムスタンプ**（最小値）をセットする。返却配列がAPI仕様上どちらの順序（昇順/降順）で返るかを**実レスポンスで確認**し、**必ず min(timestamp) を採る**こと（配列の末尾/先頭を決め打ちしない）。030では昇順/降順を取り違え、カーソルが前進せず1ページ目で自己終了した。
3. **【limit/pageSize上限の誤認識】`limit`（または pageSize）で指定した件数が"必ず"返るとは仮定しない。粒度ごとに実際の最大返却件数を実測で確認する。** 030では funding の pageSize を500と誤認（実上限100）。history-candles の1リクエスト最大返却件数を**4h/1h/15m それぞれで実測**し（例: 1回100本なのか1000本なのか）、生ログに記録する。この実測値を終了条件・進捗ログ・レート制限設計に反映する。

上記に加え、**BTC の 4h/1h/15m で「本日近辺→2019年方向」に連続タイムスタンプが単調に遡れているか**（各ページの最古足が前ページより確実に古くなっているか）を、B実装官自身がページ遷移ログで確認すること。カーソルが前進しない兆候（最古足が更新されない・同一ページの反復）を検知したら、基準を緩めず事実を明記してA/Sに差し戻す。

**あわせて実測・報告させる（Cの判断材料）**:
- 各粒度の1リクエスト最大返却件数・総ページ数・総取得本数・最古足UTC・実遡及年数（BTC/ETH別）。
- 使用した history-candles の実URL・パラメータ名（`symbol`/`productType`/`granularity`の実表記＝4h/1h/15mのコード表記は要実測・`limit`・`endTime`）・レスポンススキーマ・レート制限対応の待機設定。

### G0-2: 執行コストのモデル化（テイカー/メイカー手数料・スプレッド・スリッページ）

**本テーマ最大の生死要因**（prescreen: マイクロ構造エッジは「グロスで出た」でなく「Bitget実コスト後に残るか」が生死）。高頻度は往復コストが線形に膨らむため、Stage 0でコストを**保守的に**モデル化できるかを確認する。**対象は BTCUSDT・ETHUSDT**。

**調査手順（B実装官が実施。すべて実測・実レスポンスを正とする）**:
1. **手数料（テイカー/メイカー）の取得**: Bitget公開APIから USDT-FUTURES の手数料率を取得する。`contracts`（USDT-FUTURES）が返す `takerFeeRate`/`makerFeeRate` 相当フィールドの有無を確認し、あれば BTC/ETH の実値（bps換算）を記録。API非配信の場合は、Bitget公式手数料表（VIP0＝一般ユーザ相当）の公開値を出典URL付きで記録し、「API実測でなく公開表由来」と明記する。
2. **実効スプレッドの測定**: BTC/ETH の bid/ask を取得しスプレッドを bps で算出する。ソースは (a) `tickers`（bestBid/bestAsk 相当フィールド）または (b) orderbook トップ階層。`(ask − bid) / mid × 10000` を bps で計算。取得UTC時刻を記録（1回のみ・都合よい時刻を選ばない）。可能なら**時間帯差の参考として3〜5点の異なるUTC時刻**でスナップショットを取り、スプレッドのばらつきを併記（任意・取れれば加点情報）。
3. **板厚由来スリッページの測定**: orderbook（depth / merge-depth 相当）を取得し、**想定約定サイズごとに板を食い潰した平均約定価格 vs mid の乖離**を bps で算出する。想定サイズは固定で **$10,000 / $50,000 / $100,000（USDT建て名目）の3水準**。各サイズについて、bid側・ask側それぞれのウォーク結果（平均約定価格・mid乖離bps・板が枯れて約定しきれない場合はその旨）を記録。orderbook の取得可能階層数（何本の板が返るか）も実測記録。
4. **往復コストモデルの構築（保守的前提を固定）**: 上記1〜3から、1回転（エントリー＋イグジット）の往復コストを bps で構築する。B実装官は**判定せず**、以下2シナリオの数値を両方出す（どちらが妥当かの評価はCが行う）:
   - **(S-taker) 全成行（テイカー）想定＝保守アンカー**: 往復コスト = 2 × テイカー手数料 + 2 × (実効スプレッドの半分) + 2 × サイズ別スリッページ。**これを悲観シナリオの基準線**とする。
   - **(S-maker) 指値（メイカー）＋悲観的約定率想定**: 指値約定を仮定する場合の悲観前提を **「約定率 50%、未約定分は成行転換（テイカー手数料＋半スプレッド＋スリッページを負担）」** に固定する。往復コスト = メイカー成立分（2 × メイカー手数料）×0.5 + 成行転換分（S-taker片道相当）×0.5 を各片道に適用。**この50%約定率はStage 0の固定悲観前提であり、Stage 1で実測に基づき見直す（Stage 0では緩めない）。**
   - 各シナリオの往復コストを **$10k/$50k/$100k のサイズ別**に表で提示（サイズが増えるほどスリッページが効く様子を残す）。

**合否基準（判定はC）**:
- **達成**: BTC/ETH について、(i) テイカー/メイカー手数料、(ii) 実効スプレッド、(iii) $10k/$50k/$100k のサイズ別スリッページ、の3要素すべてが実測でき、(S-taker)(S-maker) 両シナリオの**往復コストモデルが数値で構築できている**（生データから再現可能）。
- **部分達成**: 手数料＋スプレッドは取得できたが、**orderbook depth が公開APIで十分な階層取れずスリッページを実測できない**（例: トップ数階層しか返らない）。この場合、往復コストは「手数料＋スプレッドのみ（スリッページ過小評価）」で構築し、**スリッページが未モデル化＝コストを楽観側に外している**ことを明記させる。
- **未達**: BTC/ETH の**テイカー手数料またはスプレッドのいずれかが公開手段（API・公式手数料表とも）で取得できない**（＝ネットコスト後の主ゲートが原理的に組めない）。

### G0-3: 清算/OI（建玉）履歴の可用性（路線β「清算反発」を採る場合のみ・情報ゲート）

**位置づけ**: prescreen より、清算カスケード反発を主エッジに据える場合のみ必要な追加データ。**このゲートの結果は Stage 0 の総合GO/保留を単独では左右しない**（BTC/ETH の価格＋コストが立てば mean-reversion 路線でStage 1へ進める）。**G0-3は「Stage 1のエッジ源泉事前登録で路線β(清算反発)を選べるか否か」を判断する材料を先に取っておく情報ゲート**。取れなければ路線βは mean-reversion 側に限定される（030のFunding90日枯渇と同型の可用性リスクを、Stage 1に持ち込む前にここで可視化する）。

**調査手順（B実装官が実施。BTC/ETH対象）**:
1. **公開エンドポイントの存在確認**: Bitget公開API（認証不要）に、(a) 歴史的**清算（liquidation）履歴**、(b) 歴史的**建玉（Open Interest, OI）履歴**、を返すエンドポイントが存在するかを調査。想定候補（要実測・存在しなければ「非存在」を事実記録）: open-interest 系（現在値のみか履歴を返すか）、OI履歴系、清算履歴系。叩いた実URL・パラメータ・レスポンス原文（またはHTTPエラーコード）を残す。
2. **深度の計測（存在する場合のみ）**: 存在するエンドポイントについて、G0-1同様の**空応答までのページング**で最古タイムスタンプ・総件数・実遡及年数を実測。**2022通年（2022-01-01以前から連続）をカバーするか**を判定材料として報告（清算反発の検証も2022弱気を含めたいため）。粒度（OIのサンプリング間隔＝1h毎か等）も記録。
3. **現在値スナップショットの可否**: 履歴が無くとも、現在OI・直近清算が取れるか（将来のフォワード運用でリアルタイム利用可能か）を事実記録。

**合否基準（判定はC・情報ゲート）**:
- **達成**: 清算履歴 **または** OI履歴の少なくとも一方が公開APIで存在し、**2022通年をカバーする深度**（最古 ≤ 2022-01-01・実用的なサンプリング間隔）で取得できる。＝Stage 1で路線β（清算反発）を事前登録候補にできる。
- **部分達成**: 清算/OI履歴エンドポイントは存在するが、**深度が浅く2022に届かない**（例: 直近数ヶ月〜1年のみ）。または現在値スナップショットは取れるが履歴が無い。＝路線βは直近レジームのみ or フォワード限定で検討可、2022弱気での清算反発検証は無料手段では不可。
- **未達**: 公開APIに清算履歴・OI履歴エンドポイントが**存在しない**（現在値含め非配信）。＝**路線βは mean-reversion 側に限定**（清算反発は無料手段では検証不可。有料データ判断はStage 1エッジ登録時にSへ）。

## 3. Stage 0 総合判定と分岐（判定はC・基準はここで固定）

**Cは G0-1／G0-2／G0-3 の各達成度から、次のいずれかを宣告する（A設計官が回す前に分岐ルールを固定）。G0-3は情報ゲートのため総合GO/保留の必須条件にしない（路線選択の材料）。**

| 総合判定 | 条件 | 次アクション |

## 6. 選定/確認・多重検定に関する注記（Stage 0の性質に合わせて）

- Stage 0 は**シグナル検証ではない**ため、選定/確認データ分割（過学習の炙り出し）による signal 判定は行わない。データ深度・コストは事実計測であり、探索・最適化の対象ではない。
- **Stage 0でシグナルのパラメータ（ルックバック・閾値・粒度選択・エントリー/イグジット等）を探索・最適化してはならない。** 4h/1h/15mの3粒度を測るのは「どの粒度が2022に届くか」の技術確認であって、成績を見て選ぶ対象ではない。Stage 1で使う確定粒度・エッジ源泉・パラメータは**Stage 1のspecで事前登録**する（prescreen: 短時間足はHARKingの温床＝1エッジ仮説＋1粒度＋1パラメータセット＋クリーンな確認期間の分離予約を回す前に固定）。
- 単一資産のため Stage 1 のOOSは**held-out銘柄OOSでなく時系列分割OOS**になる（prescreen）。Stage 0 で取得する短時間足は、Stage 1で時系列を選定/確認に分割できる連続性・深度を確保しておくこと（＝2022弱気を確認期間側にも配分できる深さ）。
