## 依頼された2点の疑義の解明

### 疑義1: G0-1で全6行 `candles2022:0` なのに `covers2022FullYear:true`（文字通り矛盾）

**解明＝データの矛盾ではなく「実装の半分未実装（プレースホルダ）」。結論への実害なし（Cが独立に欠損率を計算して補完・条件は真）。**

- コード `scripts/fetch-bitget-intraday.ts` L162-163 で `candles2022: 0, // placeholder` `gapRatio2022: 0, // placeholder` と**ハードコードされたプレースホルダ**。2022年内の実本数・欠損率は**一度も計算されていない**。
- `covers2022FullYear`（L142, L164）は `oldestTs <= 2022-01-01` の**片側条件のみ**を反映。specの「2022通年カバー＝最古足≤2022-01-01 **かつ** 欠損率<5%」の後半（欠損率<5%）は**未実装**。
- したがって`candles2022:0`は「2022本数が0」という事実の記録ではなく**未計算の初期値**。表記上の矛盾に見えるが、データ矛盾ではない。
- **Cによる独立補完（specの後半条件を実測）**: history-candlesで2022年区間を直接ページングして計数した結果、**BTC/ETH 4h=2180/2190本（欠損0.46%）、1h=8717/8760本（欠損0.49%）＝いずれも<<5%**。最古足も両銘柄で2019年（≤2022-01-01）を独立再現。→ **spec定義の両条件（最古足＋欠損率<5%）がともに成立**し、G0-1=達成の結論は確定する。
- **実害評価**: 結論（G0-1=達成）は不変。ただし**B実装はspecの数値化定義の半分を計算していない**。Stage 1で確定粒度の連続性を前提に検証する際、欠損の分布（どの期間にギャップが集中するか）が必要になるため、`candles2022`/`gapRatio2022`を実計算に直すことをStage 1着手前の修正項目に含める（G0-1の結論は覆らないため差し戻しではなく修正指示）。

### 疑義2: G0-2でBUYスリッページが全サイズ0.000bps、SELLがサイズ間ほぼ不変

**解明＝実装バグ2件を確定。ただし真のスリッページは板が極厚で$100kでも実質ゼロ（<0.1bps）のため、往復コスト総額（手数料主導14〜16bps）は覆らない。バグの向きはSELL過大（保守側）・BUYゼロ（楽観側だが真値も≒0）。**

Cが `merge-depth` を独立に叩いて板の並び順を確認し、`walkOrderbook` を再現した結果:

- **板の実配列（BTCUSDT実測）**: bids=**降順**（最良気配bids[0]が先頭）、asks=**昇順**（最良気配asks[0]が先頭）。best ask 1階層だけで名目**約$365k**、best bid 1階層で約$166k。＝$10k〜$100kは**最良気配1〜2階層で完全に吸収される**ほど板が厚い。

- **バグA（SELL側・明確なバグ）**: `walkOrderbook('SELL', [...orderbook.bids].reverse(), …)`（L327）。bidsは既に降順（最良が先頭）なのに `reverse()` して**最悪気配から**歩いている。C再現：
  - 正しい走査（最良bid先頭）: SELLスリッページ **≈0.008bps**（全サイズ）＝best bid 1階層で$100k吸収。
  - Bのreverse走査（最悪bid先頭）: SELLスリッページ **≈1.43bps・サイズ不変**＝可視50階層の**最悪気配**で約定価格を評価。
  - → Bの報告値（BTC SELL 2.03bps／ETH SELL 4.45bps・サイズ不変）は**可視板の底で評価した虚数**。真値は≒0.008bps。**過大評価（コスト保守側）だが数値として誤り、かつサイズ非単調**。

- **バグB（BUY側・2要因でゼロに張り付き）**:
  1. best ask 1階層の名目が約$365k → $100kまで全サイズが**asks[0]のみで約定** → avgExecutionPriceが3サイズ完全同一（BTC 63273.6）＝サイズ非依存。
  2. スリッページの基準midが**別スナップショットのticker由来**（`measureSpread`とorderbook取得が別API呼び出し・時刻差あり）。価格が下方ドリフトした結果、BUYのavgExecutionPrice（板時点のbest ask）が**ticker時点のstale midより低く**なり、`Math.max(0, …)`（L222）で**0にクランプ**。
  - → BUY=0はバグの合成。真のBUYスリッページも板の厚さから≒0（<0.1bps）だが、**測定方法として「板を最良気配から深さ方向に歩いてサイズ依存を出す」というspecの意図を満たしていない**。

- **実害評価（往復コストへの影響）**: 板が$100kに対し桁違いに厚いため、**真のスリッページは往復でも<0.2bps程度**。往復コストは**手数料主導**（taker往復12bps＋スプレッド≒0.02〜0.06bps＋真スリッページ<0.2bps ≒ **12〜13bps**、maker想定≒9〜10bps）。Bの報告値（taker 14〜16bps）はSELL過大バグで**やや保守側に上振れ**しているだけで、テーマの成立性（高頻度の往復コスト水準がモデル化できるか）は**覆らない**。
- **ただしG0-2の合否は「達成」に上げられない**: specの達成条件は「$10k/$50k/$100kのサイズ別スリッページが**実測でき**、往復コストモデルが数値で構築できている（生データから再現可能）」。スリッページ測定が**逆走査・stale mid・1階層吸収でサイズ依存を出せていない**以上、「サイズ別スリッページの実測」は成立していない。specの部分達成定義（手数料＋スプレッドは取得、スリッページ実測できず＝コストを楽観側に外している旨を明記）に該当。→ **G0-2=部分達成**。

## 判定理由（GOの根拠と条件）

1. **データ土俵は本物で深い（G0-1=達成・独立再現）**。BTC/ETHの4h/1h/15mが2019年まで連続し、2022弱気を欠損率0.5%未満でカバー。頻度軸のブレッド拡張に必要な「2022を含む複数年の短時間足」が**無料APIで立つ**ことをC自身が再現した。030を殺したサバイバーシップ・Funding枯渇の墓場を、単一資産の頻度軸で回避できている。
2. **執行コストの主要素（手数料・スプレッド）は確実（G0-2の骨格は成立）**。往復コストは手数料主導（taker 12bps／maker 9bps台）で、真のスリッページが板の厚さから≒0のため、保守的な往復コストモデルは概ね構築可能。
3. **ただしスリッページ測定スクリプトは壊れている（G0-2=部分達成の理由）**。BUYゼロ張り付き・SELL逆走査・サイズ非単調は実装バグ。今回は真値が極小なので結論は覆らないが、**Stage 1で回転率×往復コストのネットゲートを掛ける段では、サイズ・板状況次第でスリッページ成分が効く可能性があり、壊れた測定を放置できない**（prescreen必須条件③＝ネットコスト後が生死）。
4. **路線βは無料では封じられている（G0-3=未達）**。Stage 1のエッジ事前登録は mean-reversion 側に限定する材料が揃った。

→ 以上より、**総合はGO（Stage 1へ進める）**。テーマ差し戻し（Stage 0やり直し）に該当する事象（G0-2の手数料orスプレッド取得不能）は**発生していない**。

## 差し戻し（Bへ・Stage 1着手前の必須修正。テーマ差し戻しではない）

- 差し戻し先: **B実装チーム**
- 内容（Stage 1のネットコストゲートを信頼できる状態にするための修正。Stage 1 spec作成と並行可）:
  1. **バグA（SELL逆走査）修正**: `measure-bitget-execution-cost.ts` L327 の `[...orderbook.bids].reverse()` を**除去**。bidsは降順（最良気配先頭）で返るため、SELLは**最良bidから深さ方向へ**歩くのが正。
  2. **バグB（BUYゼロ張り付き）修正**: スリッページの基準midを**tickerの別スナップショットでなく、スリッページ計算に使うorderbook自身のbest bid/askから算出したmid**に統一（inter-callドリフトの混入排除）。`Math.max(0, …)`のクランプは、正しいmid基準なら符号は正になるはずで、負が出続ける場合はデータ整合を疑うログを残す。
  3. **サイズ単調性の検証を出力に追加**: 修正後、$10k<$50k<$100kでスリッページが単調増加する（または板が薄く枯れる場合はその旨）ことを生ログで自己点検。※真値が≒0でも「正しく歩いた結果ゼロ」であることを示す。
  4. **G0-1のプレースホルダ解消（軽微）**: `fetch-bitget-intraday.ts` の `candles2022`/`gapRatio2022` を実計算に直す（Cが独立補完済みで結論は不変だが、記録の正確性のため）。
- **注記**: 上記はいずれも**G0-1=達成・総合GOの結論を変えない**。真のスリッページは板の厚さから極小で、テーマの成立性は覆らない。修正は「Stage 1で誤った（過大な）スリッページを cost として引きずらない」ための衛生管理であり、Stage 0の再判定を要さない。

### 新規に検出した軽微な論点（棄却には至らないが記録＝負の資産化）

- **往復コストモデルのスプレッド二重計上（保守側・軽微）**: スリッページを**midから**測っているため、best階層約定時のスリッページ＝half-spread を既に含む。往復コスト式は `buySlip+sellSlip`（＝best約定時にfull spread相当）に**加えて** `2×(spread/2)`（＝full spread）を**別項で加算**しており、スプレッドを**約1本分二重計上**している（BTCで+0.016bps・ETHで+0.056bps程度の過大＝12bps手数料主導に対し無視可能）。**向きはコスト過大＝保守側**で偽陽性を生む方向ではないため棄却理由にはならない。Stage 1のネットコストゲート設計時にA設計官へ申し送り（スリッページをtouch基準で定義して二重計上を排すか、保守側として明示的に許容するかを事前に決めること）。
