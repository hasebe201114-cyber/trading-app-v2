**基準: 確認期間（2022-01-01〜データ末尾）で、BTC・ETH の両方が `hitRate > 50%` かつ `permutation p < 0.05`。いずれか未達なら即打ち切り。**

|---|---|---|---|---|---|---|---|---|
| BTC | confirmation | 1254 | 0.506 | **−5.8** | 0.972 | かろうじて○ | **×** | **未達** |

- **両銘柄とも permP >> 0.05（0.972 / 0.982）で p値基準を明確に外す。** → G1A 未達（片方でも未達で打ち切り、実際は両方未達）。

## permutation 実装の検証（最重要・OBS000030 Stage1の教訓）

### 結論: **permutation実装は無効（power 0）＝OBS000030 Stage1「Sharpe不変シャッフル」と同種のバグ。ただし本件の不採用結論は変えない（負のグロスで既に棄却済み）。**

`intraday-meanrev-robustness.ts` L234-258 `permutationTest`:
```
realMean = mean(realReturns)
各permで permReturns = [...realReturns] を Fisher-Yates シャッフル
permMean = mean(permReturns)
if |permMean| >= |realMean| count++
p = (count+1)/(nPerm+1)
```

**欠陥: 固定した集合を並べ替えても平均は不変（`mean` は順序に対して不変な統計量）。** よって permMean は realMean と（浮動小数点の丸め誤差を除いて）常に一致し、検定統計量が動かない＝**power 0 の無効検定**。R-bear/R-recovery/R-recent/confirmation_first_half 等で `permP=1.0` ちょうどが並ぶのはこのためで、小標本の離散分布による自然な結果ではない。confirmation の 0.9716/0.9820 が 1.0 でないのは、シャッフルで加算順序が変わったことによる**浮動小数点丸め誤差だけ**が生む微小なばらつきである。

**独立再現による裏取り（C実施）:**
1. **不変性の定量化**: 平均が明確に非ゼロの1254要素の合成リターン列を5000回シャッフルし平均を再計算 → `max|permMean − realMean| = 1.3e-18`（＝FP丸めノイズのみ）。「帰無分布」の実体は丸め誤差であり、真の並べ替え帰無分布ではない。
2. **power比較**: 平均が強く正の合成データに対し、
   - 本実装（リターン集合のシャッフル→平均再計算）: **p ≈ 0.14〜1.0**（明白な非ゼロ平均を検出できない＝無power）
   - 正しい実装（各リターンの符号をランダム反転する sign-flip permutation で「平均=0」を検定）: **p = 0.0002**（正しく有意を検出）

spec §6/§7.5/§10 は「Sharpe不変シャッフルにならないよう**リターン系列そのものを並べ替える**（030の轍を踏まない）」と明記していたが、B は「リターン系列を並べ替える」を**文字通りに実装した結果、平均不変シャッフルという同型のpower0バグ**に踏み込んだ。spec の意図（signalとreturnの結び付きを壊す）と実装（signed returnの並べ替え＝結び付きが壊れない）が乖離している。

**重要な但し書き（結論への影響）**: このバグは p値を1.0側へ偏らせる方向であり、**戦略を救う方向には働かない**。仮に permutation を正しく sign-flip で実装しても、確認期間の平均グロスは両銘柄とも負であるため、有意な正エッジは出得ない（出るとすれば「有意な負エッジ＝逆張りが逆効果」）。いずれにせよ G1A は未達。よって**permバグは判定を変えないが、B/Aへの差し戻し事項として必ず修正すること**（本OBS内の他の探索・将来の関連実験に持ち越さない）。

## 縮退リスク注記（spec §7）の実データ確認

1. **確認前半/後半どちらでもG1Aが立つか**: 立たない。BTC first_half avgBps −9.3 / second_half −2.7（両負・permP=1.0/1.0）。ETH first_half +3.0（hit0.551）だが second_half −9.6（hit0.537・permP0.997）＝後半で崩壊。片側依存以前に両側とも無エッジ。
2. **レジーム別PnL集中**: BTCは R-bear −9.0 / R-recovery −8.7 / R-recent −3.7 の全窓負。ETHは R-bear +5.4 のみ正・R-recovery −1.5・R-recent −7.6＝ETHの見かけの唯一の明るさは弱気1年（n=290）単発かつBTC非再現。特定レジーム1発依存で、しかもクロス資産で消える。
3. **BTC/ETH独立成立**: 不成立（上記チェック#3）。
4. **グロス/ネット乖離**: 本件はグロス段階で既に負のため「グロス陽性/ネット陰性の罠」以前。ネットは当然さらに悪化（sleeve netSharpe BTC −3.16 / ETH −2.10・年間トレード数≈277・年間ドラッグ≈277×12bps≈333bps/年）。
5. **permutation Sharpe不変シャッフル**: 該当（power0の無効検定・上記詳細）。spec §7.5 が最も警戒した轍を踏んでいる。

**§7 の5点すべてで脆弱性が露呈。** spec §7 末尾の「いずれかで脆弱性が露呈すればG1A〜G4Cを数値で満たしてもCは偽陽性として不採用を宣告してよい」に照らしても、そもそもG1A自体が未達である。

## 判定理由（どの罠に該当したか＝負の結果の資産化）

**罠: 「予測単位（最初の関門）から無エッジ」型（OBS000027/029/030 Stage1と同型）。**

- 確認期間（未見OOS・2022-2026）で、短時間足 microstructure mean-reversion（1h・K=3/W=168/Z=2.0/N=3・フェード）は BTC・ETH いずれも**手数料ゼロのグロス段階で平均リターンが負**。hitRateは辛うじて50%前後だが平均が負＝方向予測の生エッジが存在しない。permutation p も 0.97/0.98 で非有意。
- これは本PJが繰り返してきた「予測単位で無エッジ→パイプラインでも当然全滅」パターンの再演。sleeve netSharpe（−3.16/−2.10）・合成Sharpe（②単体を毀損）も一貫して負で、記録用参考値も全滅を裏付ける。
- 頻度軸（ブレッドを頻度で増やす・外部レビューP3）は「データ土俵は無料で立つ（Stage 0通過）」ものの、**1h平均回帰というエッジ源泉そのものが未見期間に生きていない**。②天井0.40を破る第3収益源にはならなかった。

### 限定棄却の範囲（030/029の教訓＝戦略クラス全体を一般化棄却しない）
- **棄却対象を限定**: 粒度=1h／エッジ=microstructure mean-reversion（z-scoreフェード K=3・W=168・Z=2.0・N=3・非オーバーラップ）／銘柄=BTCUSDT・ETHUSDT／期間=2022-01〜2026-07／取引所=Bitget USDT-perp。
- この限定条件下で「短期平均回帰に未見OOSの生エッジなし」を宣告する。他粒度（15m/4h）・他パラメータ・他エッジ源泉（清算反発等）・他取引所への一般化棄却は**しない**（それらは別OBSの新規起票が必要＝HARKing禁止・スコープ内乗り換え禁止）。

## 差し戻し（B検証実装官・A設計官宛て。※本実験の再測定ではない）

**本実験（EXP-OBS000031 Stage 1）は不採用・打ち切りで確定。以下は本OBS内の他探索や将来の関連実験に欠陥を持ち越さないための修正指示であり、本specの再測定・パラメータ振り直しの許可ではない。**

- **B宛て（品質欠陥）**: `permutationTest` が平均不変シャッフル（power0）。spec §7.5 が明示的に禁じた OBS000030 Stage1 と同型のバグ。将来の関連実験で使う場合は、**リターン集合の並べ替え（＝平均不変）ではなく、各トレードの符号をランダム反転する sign-flip permutation、または signal と return の結び付きを壊す並べ替え**に修正すること。本判定はこのバグが結論を変えない（負グロスで既に棄却）ことを独立確認済み。
  - なお本OBS Stage0で記録されたB信頼性ノート（1回目虚偽報告→2回目バグ残存→3回目再実行未完）に、**「4回目＝spec §7.5で名指し警告された同型バグを実装」**を追記する。事前警告済みの罠を再度踏んだ点は重い。ただし今回は生ファイル・報告文・独立再現の三者一致は取れており、虚偽報告ではない。
- **A宛て（spec表現）**: §6/§10 の「リターン系列そのものを並べ替える」という表現が、実装者に「signed returnの並べ替え」と解釈される余地を残した。将来specでは「signalとsubsequent returnの結び付きを壊す（sign-flipまたはposition-return対応のシャッフル）」と手順レベルで明示することを推奨。
