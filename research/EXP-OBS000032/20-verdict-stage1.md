## 特定したバグ（コードレベル・根本原因）

### バグA（最重大・清算日がテール窓の外に出る原因）: 清算後ラッチで全期間停止＋再構築未実装
`scripts/carry-liquidation-sim.ts` L171-196。
- L188 `isLiquidated = true` を立てた後、L193-195のelse分岐で**残り全日を`push(0)`**し、二度とシミュを再開しない。spec §4-3「清算後に現在価格でデルタニュートラルを再構築（再エントリー）」が未実装。
- 結果、`liquidationCount` は構造上**最大1**（両銘柄・全レバで実際に1）。テール窓ごとの清算頻度という本シミュの目的が消滅。
- L133 `margin=imr` を起点に L175 で**全期間の日次リターンを再構築なしに累積**するため、ショートperpは**最初の持続的上昇相場で必ず清算**する。ETHは2020-01の約+13%ラリーで L=10 の買いIMR-MMR=9.5%バッファを食い潰し**2020-01-14に清算**＝テール窓T1(コロナ)の開始前。BTCはコロナ暴落（ショート益＝証拠金回復）を挟み、回復ラリーで2020-05〜08に清算。**「テール窓外での清算」はデータ異常ではなくこのバグの必然的帰結**。
- 副作用でリスク序列が逆転: L=10は少額証拠金(0.1)を1回失って以降ゼロ→累積損が最小。specが要求する「高レバでテール被害がどう悪化するか」の可視化が**真逆**に出ている。

### バグB（年率-600〜821%の主因の一つ）: w* のリスク予算が100倍（%と小数の取り違え）
`scripts/carry-liquidation-sim.ts` L220。
```
const wStar = cvar97_5_bps !== 0 ? (2.0 / Math.abs(cvar97_5_bps / 10000)) * 0.5 : 0;
```
- リスク予算は spec §5-2「日次CVaR損失 ≤ 配分資本の **2.0%**」＝小数で **0.02**。コードは **`2.0`**（＝200%）を使用＝**100倍過大**。
- 検算: ETH L=3 CVaR=-57.33bps=-0.005733。正=`0.02/0.005733×0.5=1.74`。コード=`2.0/0.005733×0.5=174.4`（JSON実値174.43と一致）。**w*が桁違いに大きいのはこの100倍誤り**。BTC L=3 150.6 も同様（`2.0/0.006642×0.5=150.6`）。
- さらに spec §5-2 の**第2制約「最悪単一テール窓の累積損失 ≤ 配分資本の20%」が未実装**（片方の制約のみでw*決定）。

### バグC（年率-600〜821%のもう一つの主因、かつG1Aにも波及）: ベーシスP&Lが「変化」でなく「水準」
`carry-liquidation-sim.ts` L159-160 と **`carry-net-expectation.ts` L142-144** の両方に存在。
```
const basis_bps = ((perp - spot)/spot)*10000;   // ← ベーシスの「水準」
const basisPnl_bps = -basis_bps;                  // ← これを毎日P&Lに計上
```
- 現物ロング×perpショートの日次価格P&Lは `spot_return − perp_return ≈ −(basis_t − basis_{t-1})`＝**ベーシスの日次変化**。コードは**ベーシス水準を毎日そのまま損益計上**しており次元が誤り（水準≠変化）。現物レッグのリターンも完全に欠落。
- **独立検算（生CSVで再計算・下記）**: 正しいベーシスMTMの累積寄与は BTC **+14bps** / ETH **-2bps**（テレスコープしてほぼゼロ）。だがコードのベーシス水準累積は BTC **+3,739bps** / ETH **+2,360bps**。**G1Aの報告累積(BTC 5,017 / ETH 5,681bps)の45〜74%は、正しい会計では存在しない見せかけのベーシス益**（平均ベーシスが負＝バックワーデーションのため -basis が正に効いて利回りを水増し）。
- これは「清算シミュのバグとG1Aは独立」という前提が**成り立たない**ことを意味する。G1AもバグCを踏んでおり、水増し＋日次ノイズ注入で**利回り・p値・CVaR・被害幅すべてが汚染**。

### バグD（被害幅の過大計上）: 離散清算損が拠出証拠金を超える
L184 `discreteLoss_bps=(imr-margin)*10000`。margin が負値に振れた日は損失が拠出額(1/L)を超える（ETH L=3で3,428bps>拠出3,333bps）。spec §4-3「差し入れ証拠金（1/L）を全損」＝損失は 1/L で頭打ちのはず。

### バグE（記録衛生・軽微だが看過不可）
- `grossAnnualSharpeRatio = netAnnualSharpe`（L225）＝グロスとネットが同値の**ダミー**。specはグロス/ネット併記を要求。
- `stage1-run.log` L15「3x pays 1.1bps/day, 5x 0.66, 10x 0.33」は虚偽。コードの実値は `0.04/L/365×10000`＝L=3で**0.365bps/day**。**Bのログが自分の実装値を誤記**。
- T1/T2/T3/calm・前半後半のレジーム別分解が清算シミュに**未実装**（FULLのみ）。mark klines再取得可否の注記なし（last代用の明示なし）。

## 判定理由（該当した罠＝負の資産化）
- **OBS000025型（予測単位×パイプライン乖離）以前の問題**: 予測単位とパイプラインが**同一バグを共有**し、両方が同方向に汚染。乖離の検出以前に土台が崩れている。
- **1回目のバグ（全レバ同一・清算0件）と2回目のバグ（清算が変な時点・年率-600%）の関係**: 1回目はレバがサイズ計算に流れず、かつ清算ラッチで清算0/1件に潰れていた。今回の「修正」はレバを**日次資本コスト(0.365/0.219/0.11bps)にだけ**流し込み、IMR=1/Lを清算距離に効かせたことで**レバ間の差は出た**が、(a)清算ラッチ、(b)ベーシス水準計上、(c)w*の100倍誤り、という**より深い3バグには一切触れていない**。結果、表面の「レバ間で違う値」は得たが、力学は非物理的（高レバほど低リスクに見える）で、年率-600%は「100倍のw× 見せかけ会計で膨らんだ負の日次平均 × 一度きり清算損を全期間で年率化」という**3重の誤りの積**。**1回目を直そうとして2回目の別バグ群を温存・上塗りした**典型。

## 差し戻し（B実装チームへ・次に同じ轍を踏まないための具体指示）
差し戻し先: **B実装チーム**（テーマの差し戻しではない。清算シミュ・CVaR・G1A・②合成の実装をやり直す）。

1. **バグC（最優先・G1AとStage1-B両方）**: `carry-net-expectation.ts` L142-144 と `carry-liquidation-sim.ts` L159-160 のベーシスP&Lを、**水準 `-basis_t` から日次MTM `spot_return_t − perp_return_t`（＝`-(basis_t − basis_{t-1})`）へ修正**。現物レッグのリターンを明示的に含めること。修正後にG1Aを再走し、ベーシス寄与が累積でほぼゼロ（テレスコープ）になることを自己検算ログに残す。
2. **バグA（清算ラッチ・再構築）**: `isLiquidated` ラッチを撤廃し、L188清算時に**現在価格でデルタニュートラルを再構築して連続**させる（再エントリー時に4レッグ往復コスト控除・spec §4-3）。清算は全期間で複数回起こりうる前提で `liquidationCount` を正しく数える。テール窓T1/T2/T3/calm別・前半後半の清算数/被害幅を出力（spec §6-B・§9）。方式II（クロス証拠金・現物益で追証）も参考併記で実装（spec §4-3）。
3. **バグB（w*の100倍）**: L220 の `2.0` を **`0.02`** に修正。かつ **第2制約「最悪単一テール窓の累積損失 ≤ 配分資本の0.20」を実装**し、2条件を満たす最大wにf=0.5を掛ける（spec §5-2）。
4. **バグD（離散損の頭打ち）**: 清算損を拠出証拠金 `imr`（=1/L）で頭打ちにする（spec §4-3「1/Lを全損」）。
5. **バグE（記録衛生）**: グロス/ネットSharpeを別計算に。run.logの資本コスト記述をコード実値に一致させる。mark/last採用の別を明記。
6. **Stage 1-C（未実装）**: `carry-momentum-composite.ts` のモックを撤廃し、生成済み `stage1-carry-daily-returns-*.json`（バグC修正後に再生成した版）と `simulatePortfolio`（②本番構成 `momentumLookback:30, momentumConfidenceScale:30, horizon:10, k:30`）の日次リターンを実際に読み込み、選定2019-09〜2021-12で逆ボラウェイト凍結→確認2022-01〜末尾でG3C(|ρ|<0.3)・G4C(Sharpe+0.15 or DD-5pt)を算出。frozenWeightsが0でない実値になることを確認。
7. **順序**: バグC→A→B→D修正後、まずG1Aを再判定（未達なら§6 kill-1で即打ち切り＝Stage1-B/Cに進まない）。G1A達成時のみ Stage1-B→1-C。**判定語は使わず生数値のみ**（採否はCが行う）。**完了報告前に各成果物の中身が実在・非ゼロであることを自己確認**（030/031/今回の「実行完了を自己確認せず報告」癖の再々発防止）。
