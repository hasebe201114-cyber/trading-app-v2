## 0. この実験の性質（最重要・冒頭明記）

**Stage 0 は「シグナル（キャリーの利回り）の良し悪し」を一切判定しない。** キャリーが年率何%残るか、②合成でSharpeが改善するか等は**Stage 1以降で測る**ものであり、本Stage 0では**採否の文脈で測定も言及もしない**（G0-4のテール被害幅の実測は"データが組めてテールの損失分布が実測できるか"という技術確認であって、利回りの合否判定ではない）。

Stage 0 が答える問いは4つ:
> **(問1・最優先) 少なくとも1つの歴史的テールイベント（2020-03コロナ / 2022-05 LUNA / 2022-11 FTX）を含む期間の、Funding＋実perp価格＋ベーシス（perp−現物）系列を、実際に連続で調達できるか。**（G0-1）
> **(問2) その調達データ（Binance長期）が、運用取引所Bitgetのファンディング挙動を代表しうるか（符号・水準の相関）を実証的に示せるか。**（G0-2）
> **(問3) OBS026が無視した(a)実perp価格でのベーシスリスク(b)証拠金・資本コスト(c)ショートperpレッグの清算バッファ(d)レジーム反転時の4レッグ往復コスト、を実データでモデル化できるか。**（G0-3）
> **(問4) G0-1で到達したテール期間で、デルタニュートラル・ポジションの日次損益をシミュレートし、最大DD・最悪日次損失・清算発生有無を実測できるか。**（G0-4）

——純粋な**データ調達・コストモデル化・テール被害幅の実測可能性**の技術調査。シグナルの採否検証ではない。

**この性質の違いの含意**: 本テーマは027/029/030/031（予測単位で最初から無エッジ）と質的に異なり、OBS026が既に平時キャリーのプラス期待値（執行コスト控除後6-10%）を示している。ゆえにCが壊しにいく主戦場は「無エッジか」ではなく**「テール込みでも純プラスか／取引所代表性は妥当か」**であり、その真贋を問う前提となるデータ・被害幅がそもそも組めるかを本Stage 0で先に潰す。

**判定（達成/部分達成/未達・分岐GO/保留/差し戻し）はC品質チームが行う。** B実装チームは**事実・実測値・生ログのみ**を報告し、判定語（達成/未達/十分/不十分/go/no-go/取れる/取れない/問題ない/難しい/有望/割に合う 等）を使わない（後述「8. B実装官への指示」）。

## 1. 対象銘柄の定義（固定）

### 1-1. 対象銘柄＝BTC・ETH の2銘柄に固定
- prescreen前提（BTC/ETH 2銘柄・横断不要）に従い、**`BTCUSDT` と `ETHUSDT`（USDT建て無期限先物 perp ＋ 対応する現物）の2銘柄**を全ゲート（G0-1〜G0-4）の対象とする。
- 2銘柄に固定する理由: (i) BTC/ETHは廃止されないため**サバイバーシップ・バイアスは非該当**＝030を殺した壁を回避。(ii) キャリーは横断（クロスセクション）を要しない構造的プレミアム収穫であり、030 Stage2の「Funding横断枯渇」の壁も回避する。
- **銘柄を増やさないこと**。3銘柄目以降への拡張はStage 0スコープ外。

### 1-2. 2銘柄を並置する意味
- G0-1（テール到達性）・G0-3（コストモデル化）・G0-4（被害幅）は **BTCとETHの両方で独立に実測**する。片方だけで結論を出さない。2銘柄で挙動が一致するか（制約・被害幅が銘柄共通か銘柄固有か）をCが判断できる材料を残すため。

## 3. Stage 0 の合否ゲート（G0-1〜G0-4・回す前に基準を固定）

各ゲートについて「**達成 / 部分達成 / 未達**」の境界を数値・基準で定義する。**判定はCが下す**。B実装官は各基準に対応する**実測値・生データを揃えるだけ**。

### G0-1: テール到達性（＝最優先・単独の生死ゲート）

**測定対象**: BTCUSDT・ETHUSDT について、以下3系列を **Binance公開API（認証不要）** から取得し、§2のテール窓T1/T2/T3それぞれを含む連続データが実際に組めるかを実測する。

- **(a) 現物 日足OHLCV**: Binance spot klines（`https://api.binance.com/api/v3/klines?symbol=BTCUSDT&interval=1d`）。※既存 `scripts/data/btc-daily-binance-2017-2026.csv` / `eth-daily-binance-2017-2026.csv` が使えるが、**最古足・欠損・テール窓連続性を必ず再検証**（既存CSVを無検証で信用しない）。
- **(b) 実perp価格 日足**: Binance USDT-M perp klines（`https://fapi.binance.com/fapi/v1/klines?symbol=BTCUSDT&interval=1d`＝perp last price）**および** mark price klines（`https://fapi.binance.com/fapi/v1/markPriceKlines?symbol=BTCUSDT&interval=1d`）。**両方の履歴深度を実測し、テール窓を連続でカバーする方を採用**（採用した系列を明記）。これが026に欠けていた「実perp価格」＝本テーマの核。
- **(c) Funding履歴**: Binance USDT-M funding（`https://fapi.binance.com/fapi/v1/fundingRate?symbol=BTCUSDT`＝8時間おきイベント）。※既存 `btc-funding-2019-2026.csv` / `eth-funding-2019-2026.csv` が使えるが最古足・テール窓連続性を再検証。日次集計（1日3イベント＝日次合算funding）も算出。

**ベーシス系列の組み方（明記・必須）**:
- **basis_t（bps）= (perp価格_t − 現物価格_t) / 現物価格_t × 10000**。同一UTC日付の (b) perp価格（採用系列）と (a) 現物終値を突き合わせて日次ベーシスを構築する。
- perpと現物の**日付アラインメント**（同一UTC日付でのみ突合・片方欠損日はベーシス欠損として記録）を実装し、テール窓内でベーシスが連続計算できる日数・欠損日数を実測する。

**「テール窓カバー」の厳密定義（数値化）**:
- あるテール窓 Tx が「カバー成立」＝ 当該銘柄で **(a)現物・(b)perp価格・(c)funding の3系列すべてが Tx 期間を連続で持ち**、**かつ Tx 内で basis_t が計算できる日の欠損率 < 5%**（＝3系列の日付アラインメントが取れて実ベーシスが組める）。
- 参考: Binance BTC perp funding は 2019-09-19〜、ETH perp funding は 2019-11-27〜（既知・要実測確認）。ゆえに T1(2020-03) も原理上カバー可能なはずだが、**perp価格klines/mark price klinesの実履歴深度は要実測**（listing直後は薄い/欠損の可能性）。

**合否基準（判定はC。BTC・ETH両方で評価）**:
- **達成**: T1/T2/T3 の**少なくとも1窓**が、BTC・ETH**両銘柄**でカバー成立（3系列連続＋ベーシス欠損率<5%）。＝少なくとも1回の歴史的テールを実perp価格・実ベーシスで観測できる土俵が立つ。**達成の場合、Cはカバー成立した窓をG0-4のテール被害幅測定の対象として特定する。**
- **部分達成**: いずれかのテール窓が **BTCのみカバー成立し ETH は非成立**（銘柄非対称）、**または** perp価格系列が取れず funding のみ（ベーシス未構築）で窓を持てる、**または** 3窓のうち一部のみ成立し他窓はperp履歴不足で非成立。＝テールの一部/片銘柄のみ実測可能で、被害幅の観測が限定される。
- **未達**: T1/T2/T3 の**全窓**が、BTC・ETHとも「3系列連続＋ベーシス欠損率<5%」を満たさない（例: perp価格/mark price klinesの履歴がテール窓に一切届かない、または funding が枯渇）。＝実perp価格でのテール被害幅を誠実に測れない。

**⚠ ページングバグ再発防止（B実装官への必須チェックリスト・030/031の教訓）**

既存 `scripts/fetch-binance-data.ts` は終了条件に **`if (data.length < 1000) break;`（返却件数 < limit で終了）** を使っている。これは030 Stage0の`fetch-bitget-data.ts`を偽陰性で殺した「length<limit→break」バグと**同型パターン**。Binance klinesは通常密に満杯返るため顕在化しにくいが、**listing直後の薄い区間・欠損日・funding履歴の疎な区間で早期終了し、テール窓に届く前にページングを打ち切る危険がある**。以下を実装前に固定し、生ログで自己点検すること:

1. **【終了条件】ページング終了は「空応答（返却0件）」または「startTimeカーソルが現在時刻を越えた」のみで判定する。**「返却件数 < limit で終了」は**禁止**（早期打ち切りの偽陰性を生む）。空配列になるまで前進させる。
2. **【カーソル前進の取り違え】startTimeカーソルは、直前ページの返却データの"最新"タイムスタンプ + 1（時間前進）に正しく更新する。** 過去→現在方向のページングで、カーソルが前進しない兆候（同一ページの反復・最新足が更新されない）を検知したら基準を緩めず事実を明記してA/Sへ差し戻す。
3. **【1リクエスト上限の実測】** Binance klines/fundingRate の1リクエスト最大返却件数（limit上限＝klines最大1000・fundingRate最大1000だが**実測で確認**）と、レート制限（weight）を実測し生ログに記録。レート制限に配慮しリクエスト間に待機を挟む。
4. **【テール窓連続性の直接確認】** T1/T2/T3 各窓について、3系列がその日付範囲を**1日も飛ばさず**連続で持っているかをB実装官自身がログで確認し、欠損日リストを出力すること。

**あわせて実測・報告させる（Cの判断材料）**:
- BTC/ETH × (現物・perp last・perp mark・funding) 各系列の最古足UTC・最新足UTC・総本数・T1/T2/T3/calm各窓の実本数と欠損率・採用したperp系列名（last か mark か）。
- 使用した実URL・パラメータ名・レスポンススキーマ・1リクエスト上限・レート制限対応の待機設定。

### G0-2: 取引所代表性（Binance ⇔ Bitget）

**位置づけ**: prescreen G0-2＝「Binance長期でエッジ存在＋テール挙動を検証し、Bitget固有の水準・コスト・清算はフォワード/ペーパーで較正」という二段構えを採る前提で、その前提の実証的裏付け＝「BinanceのファンディングがBitgetのファンディングを符号・水準で代表しうるか」を、**両取引所で重複する直近期間（Bitget無料funding深度≈90日）**で実測する。

**調査手順（B実装官が実施）**:
1. **Bitget funding の直近履歴取得**: `scripts/fetch-bitget-data.ts`（030でバグ修正済み・ページング作法＝空応答終了/min(timestamp)カーソル/返却件数実測）を流用し、BTCUSDT/ETHUSDT の USDT-FUTURES funding 履歴を空応答まで取得（≈90日で枯渇する想定＝030実測）。最古足UTC・件数・funding間隔（8h想定）を実測。
2. **同一期間でのBinance funding抽出**: G0-1で取得したBinance funding から、Bitget側と**重複するUTC期間・同一fundingタイムスタンプ**を抽出してペア化する。
3. **代表性メトリクスの算出（BTC/ETH各々）**: 重複期間のペアデータで以下を算出:
   - **符号一致率** = sign(Binance funding) == sign(Bitget funding) の割合（%）。
   - **水準相関** = Binance funding と Bitget funding の Pearson 相関係数、および Spearman 順位相関。
   - **水準差** = (Bitget − Binance) funding の平均・標準偏差（bps/8h 換算、および年率換算）。
   - ペア数 N・重複期間（開始〜終了UTC）を明記。
4. **注記の必須出力**: 重複期間が≈90日と短いこと、テール窓（T1/T2/T3）はこの重複期間の外＝**テール時の取引所間乖離は本メトリクスでは観測できない**ことを事実として明記させる（平時の代表性のみ測っている旨）。

**合否基準（判定はC。BTC・ETH両方で評価）**:
- **達成**: BTC・ETH**両銘柄**で、重複期間の **符号一致率 ≥ 90% かつ Pearson相関 ≥ 0.8**。＝平時のファンディングは取引所間でよく相関し、キャリーが構造的プレミアムでBitgetをBinance長期で代理する二段構えが実証的に支持される（030のサバイバーシップと違い代理成立の材料）。
- **部分達成**: 符号一致率 **70〜90%** または Pearson相関 **0.5〜0.8**（片銘柄でも該当）。＝方向は概ね一致するが水準乖離があり、Bitget固有較正の重みが増す（二段構えは成立するが誤差を注記）。
- **未達**: 符号一致率 **< 70%** または Pearson相関 **< 0.5**（いずれかの銘柄で）、**または** Bitget funding が公開APIで取得できずペアが組めない。＝BinanceでBitgetを代表できない＝二段構えの前提が崩れる。

### G0-3: 執行・証拠金・清算コストのモデル化（026の未整備4項目）

**位置づけ**: OBS026が無視/簡略化した4項目 (a)〜(d) を**実データでモデル化できるか**を確認する。これらは"できる/できない"でなく"テール時に破綻しないバッファ設計の数値を実データから組めるか"で評価する（prescreen執行複雑性評価）。**対象＝BTCUSDT/ETHUSDT。**

**調査手順（B実装官が実施。すべて実測・実レスポンス/公式仕様を正とする）**:

1. **(a) 実perp価格でのベーシスリスクの統計化**: G0-1で構築した日次ベーシス系列（basis_t bps）について、**テール窓（T1/T2/T3のカバー成立分）と平時窓（calm 2021H1）それぞれ**で以下を算出:
   - ベーシスの平均・標準偏差・最小・最大（bps）、|ベーシス|の最大値（テール時に perp が現物からどこまで乖離したか）。
   - 日次ベーシス変化 Δbasis_t の標準偏差・最悪1日変化（bps）。＝デルタニュートラルが"裸"になっているベーシス方向のリスク量。
2. **(b) 証拠金・資本コストのモデル化**: Bitget/Binance の USDT-FUTURES 契約仕様から、BTC/ETH の以下を取得（API配信があればAPI、無ければ公式仕様表を出典URL付きで記録し「API実測でなく公式表由来」と明記）:
   - **維持証拠金率（maintenance margin rate）**・**最大レバレッジ**（レバレッジ階層＝ポジション名目別のmargin tierがあれば代表2〜3階層を記録）。Bitget contracts エンドポイント（`contracts?productType=USDT-FUTURES`）の該当フィールドを実測確認。
   - これを用いて**資本コストのモデル式を固定**: 本Stage 0では **現物ロングレッグ＝全額自己資本で保有（レバレッジ無し・借入コスト0）、ショートperpレッグ＝名目に対し初期証拠金 IM を差し入れ**とする。資本コスト率は保守アンカーとして **年率4%**（無リスク金利相当・USDT建て機会費用）を固定前提とし、必要証拠金 × 4%/年 を資本コストとしてモデルに乗せる（この4%はStage 0固定前提。Stage 1で見直し）。
3. **(c) ショートperpレッグの清算バッファのモデル化**: (b)の維持証拠金率・レバレッジ設定から、**ショートperpレッグの清算価格**を算出する式を固定し、実データで検証:
   - 想定レバレッジを保守的に **3倍（IM≈33%）** に固定（Stage 0前提。デルタニュートラルは方向中立でも perp レッグは単独で証拠金を食い、価格急騰時にショートperpが清算され得る）。清算価格 ≈ エントリー価格 × (1 + IM − 維持証拠金率)（ショート方向・正確な式は取引所仕様で確認して実装）。
   - G0-1のテール窓の**実perp高値**が清算価格に到達したか（＝ショートperpレッグが清算されたか）を各テール窓で判定材料として実測（清算発生フラグ）。デルタニュートラルの現物ロング側の含み益と相殺される前にレッグが飛ぶ離散イベントリスクを可視化。
4. **(d) レジーム反転時の4レッグ往復コストのモデル化**: `funding-carry-delta-neutral.ts` の FLIP_COST ロジック（2レッグ×往復＝4×片道コスト）を、Bitget実コストで再構築する。片道コスト＝Bitgetテイカー手数料（031実測＝6bps）＋実効スプレッド（031実測＝BTC0.016/ETH0.056bps）＋板厚スリッページ（031実測＝BTC/ETHとも板極厚で≒0、$100kまで<0.2bps往復）。1回転の4レッグ往復コストをbpsで構築。

**合否基準（判定はC）**:
- **達成**: BTC/ETH について、(a)ベーシス統計・(b)維持証拠金率/レバレッジと資本コスト式・(c)清算価格式とテール窓での清算発生判定・(d)4レッグ往復コスト、の**4項目すべてが実データ/実仕様から数値で構築できている**（生データから再現可能）。
- **部分達成**: (a)(d)は構築できたが、(b)維持証拠金率/レバレッジ階層が公開API・公式表とも取得できず**清算価格(c)が保守的仮定でしか置けない**（例: 維持証拠金率を業界標準値で仮置き）。この場合、仮置き値と出典を明記させ「実仕様でなく仮定」であることを開示。
- **未達**: (a)ベーシス統計が組めない（＝G0-1でperp価格が取れずベーシス未構築）、**または** (d)の手数料が取得できず往復コストが組めない。＝コストモデルの根幹が原理的に組めない。

### G0-4: テールイベント被害幅の実測

**位置づけ**: 本テーマの生死＝テール被害幅。G0-1で到達したテール窓で、デルタニュートラル・ポジションの**実損益分布**を実perp価格ベーシスで実測する。**これはシグナルの利回り採否判定ではなく、"被害幅が実測できるか＋その大きさ"の技術確認。**

**調査手順（B実装官が実施。G0-1でカバー成立したテール窓・平時窓が対象。BTC/ETH各々）**:

1. **デルタニュートラル・ポジションの構成（固定）**: **現物ロング×perpショート、等ノーション**（各レッグ名目＝$1（正規化）で日次損益をbps単位で算出）。ファンディングが正のときショートperpが受取（本テーマの平時の収益源）。方向は固定（026のような平滑化窓での符号反転は**Stage 0では行わない**＝反転はシグナル最適化＝Stage 1の対象。Stage 0は"素の"デルタニュートラルでテール被害を測る）。
2. **日次損益の構築（026の穴を埋める＝実perp価格ベーシスP&Lを必ず加える）**:
   - **funding P&L_t** = 日次合算funding（ショート側が受取＝ +funding_t、名目に対する率）。
   - **ベーシスP&L_t** = 現物ロング×perpショート等ノーションの価格方向以外の残差 = ノーション × [ (現物_t/現物_{t-1} − 1) − (perp_t/perp_{t-1} − 1) ]。＝実質 −Δbasis に相当。**026が現物代用で0にしていた項をここで実perp価格から実測する（本Stage 0の核心）。**
   - **日次P&L_t** = funding P&L_t + ベーシスP&L_t。（初日のエントリー往復コスト・平時の資本コストは別途 G0-3(b)(d) の値を注記として併記。テール窓内の日次リバランスコストはStage 0では0とし、コストはG0-3で別建て提示＝被害幅の主機構であるベーシス+清算を純粋に見る）。
3. **被害幅メトリクスの算出（各テール窓・平時窓・BTC/ETH別）**:
   - **累積P&L**（窓全体、bps）。
   - **最大ドローダウン**（窓内のP&L累積曲線の peak-to-trough、bps）。
   - **最悪日次損失**（single worst day、bps）。
   - **清算発生フラグ**: G0-3(c)の清算価格に窓内の実perp高値が到達したか（到達＝ショートperpレッグ清算＝離散イベントで中立崩壊）。
   - **平時窓との対比**: calm窓での日次P&Lの平均・標準偏差を併記し、「平時の小益 vs テールの鋭い損失」の非対称（左テール）が実データで可視化されるかを示す。
4. **参考出力（判定に使わないが記録）**: OBS026が現物代用で出した数値との差＝「実perp価格を入れるとベーシスP&Lがどれだけ被害を増やすか」を対比できるよう、ベーシスP&L項を0にした場合（＝026相当）の被害幅も併記（026の楽観が実perpでどれだけ悪化するかの可視化。**判定はCが行う**）。

**合否基準（判定はC）**:
- **達成**: G0-1でカバー成立した**少なくとも1テール窓**について、BTC・ETH（カバー成立した銘柄）で、実perp価格ベーシスP&Lを含む日次損益から**最大DD・最悪日次損失・清算発生フラグが数値で算出できている**（生データから再現可能）。＝テール被害幅を実測できる。
- **部分達成**: 被害幅は算出できたが、**ベーシスP&Lが実perp価格でなく現物代用（026相当）でしか組めない**（G0-1でperp価格が届かず）、**または** 清算フラグがG0-3(c)未成立で判定できない。＝被害幅の主機構の一部が未測定。
- **未達**: 被害幅メトリクスが一切算出できない（G0-1で全テール窓が非カバー＝データが組めない）。
