## 0. 仮説フレームワークと目標値

> **設計思想**: 目標利率は「希望値」ではなく「検証可能な仮説が成立した場合の期待値」として導出する。
> 仮説が崩れた時点で目標も再設定する。フォワード較正（F1〜F4）は各仮説の検証装置として位置づける。

### 0-1. 戦略仮説一覧

| # | 仮説 | 検証ゲート | 成立条件 |
|---|---|---|---|
| H1 | Bitget perp の funding rate は長期的に正の期待値を持つ（キャリープレミアム持続性） | F1 | 90日累積キャリー > 0 かつ 日次平均 ≥ 下限（BTC 0.039 / ETH 0.003 bps） |
| H2 | Bitget の funding 符号は Binance と 80% 以上一致する（データ代表性） | F2 | 8hイベント単位 sign agreement ≥ 80% |
| H3 | ライブ環境で清算・追証は発生しない（リスク管理の有効性） | F3 | 90日間 清算 0件・追証 0件 |
| H4 | Basis の日次変動は tail リスク許容水準以内（市場構造安定性） | F4 | Basis日次変化 std ≤ T1（BTC 12.14 / ETH 19.47 bps） |
| H5 | キャリー×モメンタムの相関は |ρ| < 0.3 を維持（スリーブ直交性） | ライブ P&L 相関 | 両スリーブ稼働後に計測 |

### 0-2. 仮説条件付き目標値（シナリオ分岐）

#### ベースシナリオ：H1〜H4 全て成立（フォワード較正合格）

| KPI | 目標値 | 根拠 |
|---|---|---|
| 年率リターン（口座エクイティ比） | **20〜30%** | 全期間平均 funding × w*（BTC 5.76 bps/day × 365 ≈ 21%、ETH 8.97 bps × 365 ≈ 33%）|
| Sharpe（合成ポートフォリオ） | **≥ 1.5** | North Star KPI |
| 最大ドローダウン（目標） | **< 10%** | バックテスト実績 6.47% を基準に保守マージン |
| 最大ドローダウン（許容上限） | **< 20%** | サーキットブレーカー発火閾値 |
| 月次勝率（P&L > 0 の月数比） | **≥ 70%** | キャリー戦略の特性（連続負け月が少ない）|

#### 保守シナリオ：H1 部分成立（funding rate が低い環境）

> 条件: 日次平均 funding が calm 窓基準（BTC 11.62 / ETH 14.40 bps）を大幅に下回るが正値

| KPI | 想定値 | 対応 |
|---|---|---|
| 年率リターン | **5〜15%** | 戦略継続（positive expectancy は維持） |
| Sharpe | **0.8〜1.2** | 目標未達だが許容範囲 |
| Max DD | **< 15%** | w* の縮小検討（2.0〜2.5×へ） |
| 判断トリガー | 3ヶ月移動平均リターン < 5% | A設計チームへ w* 再較正依頼 |

#### ストレスシナリオ：H1 不成立（funding が持続的にマイナス）

> 条件: F1 警告（累積キャリーがマイナスに転落 または 10日連続でマイナス）

| KPI | 想定値 | 対応 |
|---|---|---|
| 年率リターン | **マイナス** | 戦略一時停止 |
| 対応アクション | **司令塔への即時エスカレーション** | F1 警告発火後 5 営業日以内に判断 |
| 再開条件 | funding 環境の回復確認（14日移動平均が正に転換） | A設計チームが回復判定を実施 |

### 0-3. 仮説検証サイクル

```
[フォワード較正中（〜2026-10）]
  H1〜H4 を F1〜F4 ゲートで継続検証（試験値フェーズ）
          ↓
[C 較正監査（2026-10-02）]
  全仮説の正式判定 → ベース/保守/ストレスシナリオを確定
          ↓
[Phase 1 稼働開始後]
  月次レビュー: 実績 vs ベースシナリオを比較
  四半期レビュー: 仮説の再評価（環境変化があれば w* 再較正）
          ↓
[Phase 2 以降]
  H5（スリーブ直交性）の検証開始
  OBS000034 マルチスリーブ配分の仮説を新規設定
```

### 0-4. 各仮説が崩れた場合のアクション

| 仮説 | 崩壊シグナル | 即時アクション | 中期アクション |
|---|---|---|---|
| H1 | 累積キャリーがマイナス転落 | ポジション削減 50% | A設計チームへ戦略見直し依頼 |
| H2 | F2 sign agreement < 70% | 新規エントリー停止 | 参照取引所を OKX 等に変更（A設計） |
| H3 | 清算・追証が 1 件でも発生 | 全ポジション即時決済 | w* を半減・原因究明 |
| H4 | Basis std が T1 × 2 超 | 新規エントリー停止 | 市場構造の変化を確認後に再開 |
| H5 | |ρ| が 0.3 超を 30 日持続 | スリーブ配分を再計算 | OBS000034 の仮説更新 |

## 3. キャリースリーブ実行フロー

### 3-1. スケジュール
```
Bitget USDT-M Perp のfunding決済: 00:00 / 08:00 / 16:00 UTC
自動実行タイミング: 各決済の30分前 → 23:30 / 07:30 / 15:30 UTC
理由: 決済直前に funding が反転する場合の対応マージン
```

### 3-2. 実行フロー（8h ごと）
```
[START] 8h cron 起動
  ↓
[STEP 1] Bitget API から最新 funding rate 取得（BTC/ETH）
  ↓
[STEP 2] SMA-7 シグナル計算 → signal_pos ∈ {+1, −1}
         +1: funding が正（long side が funding を受け取る）
         −1: funding が負（flat のまま）
  ↓
[STEP 3] 現在ポジション取得（perp long + spot short）
  ↓
[STEP 4] シグナル比較
  ├─ 変化なし → ログのみ → END
  └─ 変化あり → STEP 5 へ
  ↓
[STEP 5] サーキットブレーカー判定
  ├─ halted=true → アラート送信 → END (ポジション維持)
  └─ halted=false → STEP 6 へ
  ↓
[STEP 6] 目標ポジション計算
         Notional = w* × 口座エクイティ（USDT）
         BTC notional = 3.629 × equity
         ETH notional = 3.789 × equity
  ↓
[STEP 7] 差分注文発注
         signal +1: Long perp（まだなければ）+ Short spot（delta hedge）
         signal −1: Close perp + Close spot short
  ↓
[STEP 8] 約定確認（ポーリング or webhook）
  ↓
[STEP 9] 実行ログ記録（JSON ledger commit to GitHub）
  ↓
[END]
```

### 3-3. デルタニュートラル実装
```
Long leg : Bitget USDT-M Perpetual (BTCUSDT)
           サイズ = w* × equity / BTC_price
Short leg: Bitget Spot Margin (BTC/USDT)
           BTC を借りて売却 → delta hedge
           ※金利コスト (borrow rate) が運用コストに加算

目標状態: BTC perp long N枚 + BTC spot short N枚 = ネット delta ≈ 0
         P&L = funding 受取 − perp 手数料 − borrow 金利 − スリッページ
```

**設計上の注意点**:
- Spot short の実現には Bitget マージン口座の BTC 借入設定が必要
- borrow rate が高騰した場合は収益性が低下する（F1 フォワードで確認中）
- 代替案: Spot short の代わりに COIN-M Perp 売り（basis リスクが追加されるが借入不要）

## 4. Bitget API 統合設計

### 4-1. 必要なエンドポイント
| 用途 | エンドポイント | 認証 |
|---|---|---|
| 口座残高 | `GET /api/v2/mix/account/account` | 要 |
| 現在ポジション | `GET /api/v2/mix/position/allPosition` | 要 |
| 注文発注 | `POST /api/v2/mix/order/placeOrder` | 要 |
| 注文確認 | `GET /api/v2/mix/order/detail` | 要 |
| Spot 残高 | `GET /api/v2/spot/account/assets` | 要 |
| Spot 注文 | `POST /api/v2/spot/trade/placeOrder` | 要 |
| Funding rate 取得 | `GET /api/v2/mix/market/funding-rate` | 不要 |
| Funding 履歴 | `GET /api/v2/mix/market/history-fund-rate` | 不要 |

### 4-2. API キー管理
```
本番執行用キー（APIキー種別: 取引許可）
  → GitHub Secrets: BITGET_API_KEY, BITGET_SECRET, BITGET_PASSPHRASE

監視専用キー（APIキー種別: 読み取り専用）
  → 残高確認・ポジション確認のみに使用（最小権限原則）

禁止: 出金許可を持つAPIキーの使用
禁止: APIキーをコードにハードコード・コミット
```

### 4-3. レート制限対応
- Bitget API: エンドポイントごとに 20〜100 req/sec
- 実行スクリプトは 8h に 1 回の起動のため制限に余裕あり
- リトライ: 429 エラーで指数バックオフ（2s/4s/8s）

## 5. リスク管理レイヤー

### 5-1. サーキットブレーカー（既存 `src/risk-layer/circuitBreaker.ts` を本番対応へ拡張）
| トリガー | 閾値 | アクション |
|---|---|---|
| 最大ドローダウン超過 | 20% | 全ポジション決済 ＋ 全面停止（司令塔通知必須） |
| 当日損失超過 | 5% | 新規エントリー停止（既存ポジション維持） |
| 清算発生 | 1件以上 | 全ポジション決済 ＋ 全面停止（即時アラート） |
| Basis スパイク | DD std > T1×2 | 新規エントリー停止 ＋ 警告 |
| データギャップ | 3日以上欠損 | 警告（自動停止はしない） |

### 5-2. ポジションサイズ上限
| 項目 | 上限 |
|---|---|
| 単一資産あたりレバレッジ（Perp leg） | 5× |
| 単一資産あたりレバレッジ（Spot short leg） | 5× |
| BTC + ETH 合計ノショナル / 口座エクイティ | 10× |
| Phase 1 最小稼働ロット | $500〜1,000 （初期安全帯） |

### 5-3. 緊急停止（キルスイッチ）
```
手動: scripts/emergency-close.ts --all
      → 全ポジションを成行決済
      → GitHub Secrets の LIVE_MODE フラグを false に切替

自動: サーキットブレーカー発火時に同スクリプトを自動呼出し
```
