## 0. 仮説フレームワークと目標値

> **設計思想**: 目標利率は「希望値」ではなく「検証可能な仮説が成立した場合の期待値」として導出する。
> 仮説が崩れた時点で目標も再設定する。フォワード較正（F1〜F4）は各仮説の検証装置として位置づける。

### 0-1. 戦略仮説一覧

| # | 仮説 | 検証ゲート | 成立条件 |
|---|---|---|---|
| H1 | Bitget perp の funding rate は長期的に正の期待値を持つ（キャリープレミアム持続性） | F1 | 90日累積キャリー > 0 かつ 日次平均 ≥ 下限（BTC 0.039 / ETH 0.003 bps） |
| H2 | Bitget の funding 符号は Binance と 80% 以上一致する（データ代表性） | F2 | 8hイベント単位 sign agreement ≥ 80% |
| H3 | ライブ環境で清算・追証は発生しない（リスク管理の有効性） | F3 | 90日間 清算 0件・追証 0件 |
| H4 | Basis の日次変動は tail リスク許容水準以内（市場構造安定性） | F4 | Basis日次変化 std ≤ T1（BTC 12.14 / ETH 19.47 bps） |
| H5 | キャリー×モメンタムの相関は |ρ| < 0.3 を維持（スリーブ直交性） | ライブ P&L 相関 | 両スリーブ稼働後に計測 |

### 0-2. 仮説条件付き目標値（シナリオ分岐）

#### ベースシナリオ：H1〜H4 全て成立（フォワード較正合格）

| KPI | 目標値 | 根拠 |
|---|---|---|
| 年率リターン（**配分資本＝証拠金相当額ベース**） | **20〜30%** | 全期間平均 funding × w*（BTC 5.76 bps/day × 365 ≈ 21%、ETH 8.97 bps × 365 ≈ 33%）。⚠ 「口座エクイティ比」ではなく配分資本（証拠金予算）に対する名目利回り。投資家が実際に用意する総資金（現物フルキャッシュ購入＋perp証拠金の合計）に対する実効利回りは、perpレバレッジ3倍前提で約1/4.3〜1/5.1に薄まる（0-5節参照。Web `/forward`画面の損益シミュレーションと同一の換算ロジック） |
| Sharpe（合成ポートフォリオ） | **≥ 1.5** | North Star KPI（Sharpeはスケール不変のため配分資本/総資金どちらのベースでも同値） |
| 最大ドローダウン（目標） | **< 10%** | バックテスト実績 6.47% を基準に保守マージン |
| 最大ドローダウン（許容上限） | **< 20%** | サーキットブレーカー発火閾値 |
| 月次勝率（P&L > 0 の月数比） | **≥ 70%** | キャリー戦略の特性（連続負け月が少ない）|

#### 保守シナリオ：H1 部分成立（funding rate が低い環境）

> 条件: 日次平均 funding が calm 窓基準（BTC 11.62 / ETH 14.40 bps）を大幅に下回るが正値

| KPI | 想定値 | 対応 |
|---|---|---|
| 年率リターン | **5〜15%** | 戦略継続（positive expectancy は維持） |
| Sharpe | **0.8〜1.2** | 目標未達だが許容範囲 |
| Max DD | **< 15%** | w* の縮小検討（2.0〜2.5×へ） |
| 判断トリガー | 3ヶ月移動平均リターン < 5% | A設計チームへ w* 再較正依頼 |

#### ストレスシナリオ：H1 不成立（funding が持続的にマイナス）

> 条件: F1 警告（累積キャリーがマイナスに転落 または 10日連続でマイナス）

| KPI | 想定値 | 対応 |
|---|---|---|
| 年率リターン | **マイナス** | 戦略一時停止 |
| 対応アクション | **司令塔への即時エスカレーション** | F1 警告発火後 5 営業日以内に判断 |

### 0-5. 資金運用方針（単利/複利）— 2026-07-12 司令塔判断

**司令塔判断（確定）**: 検証POC段階（フォワード較正〜Phase 1初期）は**単利（配分資本固定）**で進める。複利運用（口座エクイティ連動のポジション拡大）を採用するかどうかは、**実行フェーズで改めて検討する**未決事項として扱う。

**現状のPOC・実装は単利設計で一貫している**（今回の是正で本ドキュメントもこれに整合させた）:
- `bitget-carry-forward-paper.ts`（フォワード較正会計）: `w*`は固定値を参照するのみで、証拠金残高（`margin_t`）の増減に応じて再計算されることはない
- `btc-carry-executor`（`open-position.ts`/`execute-daily.ts`）: 固定の環境変数`CAPITAL_USDT`を使い、反転（シグナル変化）のたびに固定資本ベースでポジションを再構築する
- ゆえにF1〜F4ゲート・Sharpe/DD等の検証結果はすべて「単利・配分資本固定」を前提にしたもの

**複利化を実行フェーズで検討する際の懸念事項**（2026-07-12 司令塔とのセッションで洗い出し）:
1. **w*（CVaR基準サイジング）の前提が崩れる**: `w*`（BTC 3.629 / ETH 3.789）はStage 1で「配分資本が固定」という前提のもと、日次CVaR制約（≈27bps）から逆算された値。複利化（含み益に応じてポジション拡大）すると、この制約の意味が変わり、連勝後に最大ポジションでテールを迎える増幅リスクが生じる。採用する場合は**w*の再導出または追加のCVaR再検証が必須**。
2. **テール未観測問題との複合リスク**: 本戦略はBitget無料データではコロナ級テールが観測できていない弱点を抱える（STRATEGY-BRIEF既知）。複利は「資金が増えたタイミングでテールが来ると損失絶対額も増える」性質があり、テール耐性が未検証な戦略とは相性が悪い。
3. **PJ000001 Phase5（段階的資金拡大）との混同回避**: PJ000001 §5.2 Phase5「実資金段階導入」の「3ヶ月実績を見て段階的に資金を拡大」は**司令塔が意図的に判断する人間主導のプロセス**であり、システムが自動的に複利再投資することとは異なる。実行フェーズ設計時にこの2つを明確に区別すること。
4. **追加のC監査が必要**: 複利化を採用する場合、「口座エクイティ」の定義（未実現損益を含むか、実現損益のみか等）を仕様化し、既存のF1〜F4とは別の検証ゲートとしてC品質チームの監査を経ること。

## 3. キャリースリーブ実行フロー

### 3-1. スケジュール
```
Bitget USDT-M Perp のfunding決済: 00:00 / 08:00 / 16:00 UTC
自動実行タイミング: 各決済の30分前 → 23:30 / 07:30 / 15:30 UTC
理由: 決済直前に funding が反転する場合の対応マージン
```

### 3-2. 実行フロー（8h ごと）
```
[START] 8h cron 起動
  ↓
[STEP 1] Bitget API から最新 funding rate 取得（BTC/ETH）
  ↓
[STEP 2] SMA-7 シグナル計算
         "open" : funding が正（sma_bps > threshold）
         "close": funding が負（sma_bps ≤ threshold）
         ⚠ Stage1 spec（`00-spec-stage1.md`§2）は funding負転時に「現物ショート×
           perpロング」への反転（逆キャリー収穫）を定義しているが、実際のexecutor
           実装（`execute-daily.ts`）はこれを実装しておらず、"close"時は単純に
           ポジションをフラット化するのみ。詳細・影響は3-3節・課題#9参照。
  ↓
[STEP 3] 現在ポジション取得（spot long + perp short）
  ↓
[STEP 4] シグナル比較
  ├─ 変化なし → ログのみ → END
  └─ 変化あり → STEP 5 へ
  ↓
[STEP 5] サーキットブレーカー判定
  ├─ halted=true → アラート送信 → END (ポジション維持)
  └─ halted=false → STEP 6 へ
  ↓
[STEP 6] 目標ポジション計算（⚠ 単利・配分資本固定。0-5節参照）
         Notional = w* × 配分資本（USDT・固定値。反転のたびに口座エクイティで
                    再計算しない＝POC/フォワード較正と同一設計）
         BTC notional = 3.629 × 配分資本
         ETH notional = 3.789 × 配分資本
         （複利化＝口座エクイティ連動サイジングは実行フェーズの検討事項。採用時は
           w*再導出・追加C監査が前提。0-5節参照）
  ↓
[STEP 7] 差分注文発注
         signal "open" : Long spot（まだなければ・全額自己資本）+ Short perp（delta hedge）
         signal "close": Close spot long + Close perp short（フラット化。
                          現物ショート×perpロングへの反転は行わない＝課題#9）
  ↓
[STEP 8] 約定確認（ポーリング or webhook）
  ↓
[STEP 9] 実行ログ記録（JSON ledger commit to GitHub）
  ↓
[END]
```

### 3-3. デルタニュートラル実装

**(A) 順キャリー構成（funding正・現物ロング×perpショート）— specでも実装でも一致**
```
Long leg : Bitget Spot (BTC/USDT)
           サイズ = w* × 配分資本 / BTC_price（全額自己資本・借入なし・レバレッジなし）
Short leg: Bitget USDT-M Perp (BTCUSDT)
           サイズ = Long legと同数量（デルタニュートラル）
           証拠金 = ノーショナル / perpレバレッジ（採否判定帯は3倍・IMR=1/3。
                    executor暫定値5倍との不一致は課題#3参照）

目標状態: BTC spot long N枚 + BTC perp short N枚 = ネット delta ≈ 0
         P&L = funding 受取 − perp 手数料 − 資本コスト − スリッページ
```
現物レッグは全額自己資本のため、スポットマージンの借入（borrow rate）は発生しない（`00-spec-forward-calibration.md`§0-3・`00-spec-stage1.md`§3で確定）。

**(B) 反転構成（funding負・逆キャリー）— ⚠ specと実装が食い違う（課題#9・2026-07-12発覚）**

`00-spec-stage1.md`§2は以下を定義している:
```
sign(SMA_7(funding_daily)) < 0 → 現物ショート×perpロング（反転・逆キャリー・
                                   ロングperpが受取＝弱気でfunding負転時に
                                   払う側に回らない）
```
現物を「ショート」するには、通常Bitgetのスポットマージン（借入）が必要になる。しかし:
- **Stage1 specの会計モデル自体、この反転構成の借入コストを計上していない**（資本コストの定義は「ショートperp証拠金×年率4%」のみ・`00-spec-stage1.md` line 104/133）。ペーパートレード（`bitget-carry-forward-paper.ts`）では損益計算式の符号を反転させるだけで済むため、この簡略化が表面化しなかった。
- **実際の`btc-carry-executor`は、この反転構成を一切実装していない**。`execute-daily.ts`の`computeSignal()`はシグナルを`"open"`/`"close"`の2値でしか返さず、`"close"`時は`closeDeltaNeutral()`でポジションをフラット化するのみ。「spot short + perp long」を新規に開く処理はコード上どこにも存在しない。

**含意**: Stage1 specが検証した戦略は「順キャリー＋逆キャリーの両取り」だが、実運用（btc-carry-executor）が実行するのは「順キャリーのみ・逆局面はフラット（現金化）」という、より単純で保守的な戦略。
- リスク面：現物ショートの借入コスト・追加の清算リスクを回避できる（保守的）
- 収益面：バックテスト（F1参照値等）は両方向の合算期待値のため、順キャリーのみの実運用実績と単純比較すると、バックテスト参照値がやや過大（逆キャリー局面の収益分を含む）である可能性がある

**設計上の注意点**:
- 投資家が実際に用意する総資金は「現物購入額＋perp証拠金額」の合計。perpレバレッジ3倍の場合、総資金の75%が現物購入・25%がperp証拠金という内訳になる（0-5節・Web `/forward`画面の損益シミュレーションと同一ロジック）
