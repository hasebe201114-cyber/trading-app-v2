# PJ000002 - マルチエージェント運営計画書

## ステータス

- 個別の開発件名ライフサイクル（`01開発アイデア`〜`90解決済`）には乗せない。**運営体制が続く限りクローズしない**。見直しは変更履歴に追記して継続更新する。

## 1. 目的とねらい

プロジェクトの最優先事項は「トレード判定ロジックを信頼性の高いものとし本番運用できるようにする」こと（PJ000001）。
その最大のリスクは **「検証の甘さによる偽陽性（過学習・蜃気楼シグナルの採用）」** である。実際、これまで
「予測単位では有望でもポートフォリオ水準で全滅」というパターン（ERゲート＝蜃気楼、レジームスイッチ＝パイプラインで悪化、Funding方向性版＝不採用）を繰り返してきた。

本計画書は、この偽陽性リスクを **役割分担の構造そのもの** で潰すためのマルチエージェント運営を定める。
また、ユーザー（司令塔）は「スマホ指示・オペレーション極小」を要件とするため、判断以外の作業をエージェントへ委譲し、司令塔の負荷を最小化する。

## 2. 体制（6体：1本の実験ライン ＋ 1つの頭脳）

```
        ┌─────────────────────────────────────────────┐
        │            司令塔（ユーザー）＝最終意思決定    │
        └───────▲───────────────────────────┬─────────┘
        具申・作戦提案 │                       │ テーマ・GO
                      │                       ▼
        ┌─────────────┴───────────────────────────────────┐
        │  S 戦略参謀官（CIO）  ← パイプラインの"上"の頭脳    │
        │  ・仮説の事前目利き（筋の悪い案を安く却下）        │
        │  ・KPI/台帳で全体監視、横断パターン検出            │
        │  ・週次で作戦ブリーフを司令塔へ具申                │
        └──┬──────────────────────────────────▲───────────┘
    目利き済みの方向 │                         │ 整った記録・判定・本番指標を吸い上げ
                    ▼                         │
   ┌──── 実験パイプライン（1実験=1バケツ）─────────────────┐
   │  A 設計官 → B 検証実装 → C 懐疑検証 →(GO)→ D 統合反映   │
   │                                    └──────► E 記録進行 ─┘
   └────────────────────────────────────────────────────────┘
```

- **横軸（A→E）＝実験を1件流すライン作業**
- **縦軸（S）＝ライン全体を監督し、司令塔に助言する頭脳**（フェーズではなくオーバーレイ。ループを閉じる）

### 2.1 各エージェントの役割

| 記号 | 名称 | agent定義 | 担当フェーズ | 役割の核 | 主要成果物 |
|---|---|---|---|---|---|
| **S** | 戦略参謀官（Chief Strategist / CIO） | `.claude/agents/chief-strategist.md` | 全体横断・上位 | クリプト市場の目利き＋全体監視で「どこへ向かうか・勝てているか」を具申 | `research/00-prescreen.md`, `STRATEGY-BRIEF.md`, `portfolio-ledger.md` |
| **A** | 戦略設計官（Strategy Architect） | `.claude/agents/strategy-architect.md` | 提案→計画 | 仮説を反証可能な実験仕様に落とす。成功基準を回す前に確定 | `research/EXP-*/00-spec.md` |
| **B** | 検証実装官（Quant Researcher） | `.claude/agents/quant-researcher.md` | 実装調査→実装 | specに忠実に実装・実行。予測単位＋パイプライン両方の生データを出す | `research/EXP-*/10-result/` |
| **C** | 懐疑検証官（Adversarial Reviewer） | `.claude/agents/adversarial-reviewer.md` | 再チェック（最重要） | 好結果を壊しにいく。偽陽性の最終防波堤。採用/不採用を宣告 | `research/EXP-*/20-review.md` |
| **D** | 統合反映官（Integration & Deploy） | `.claude/agents/integration-deploy.md` | 反映 | 採用＋司令塔GOのものだけ本番へ統合・デプロイ | `research/EXP-*/30-decision.md` |
| **E** | 記録進行官（Archivist / PM） | `.claude/agents/archivist-pm.md` | 全工程横断 | OBS移動＋リンク修正、方針変更履歴、引き継ぎ書、ACTIVE更新 | OBS件名, 引き継ぎ書, `ACTIVE.md` |

### 2.2 役割境界（重複を防ぐ3つの問い）
- **S参謀官**：「どこへ向かうべきか・勝てているか」＝戦略・判断・市場ドメイン
- **A設計官**：「選んだ仮説をどう厳密に検証するか」＝方法論・実験設計
- **E記録進行官**：「記録は整合しているか」＝事務・整合維持

S（向かう先を決める）→ A（検証仕様に落とす）→ B/C/D → E（記録を整える）→ 整った記録をSが読んで次を具申。
SとCは健全な対立関係（Sは市場確信の楽観的提案者、Cはそれを壊す悲観的検証者）。この緊張が偽陽性と機会損失の両方を抑える。

## 3. フォルダ・ファイル構成

「実験1件＝フォルダ1つ＝OBS件名1つ」を1:1に固定し、その1フォルダを6体が順に手渡す「バケツ」とする。

```
trading-app-v2/
├─ .claude/agents/        ← 各エージェントの指示書（6ファイル）
├─ research/              ← 新設：エージェント間バケツリレー作業場（揮発してよい生成物）
│  ├─ ACTIVE.md           ← E管理：進行状況の信号機
│  ├─ STRATEGY-BRIEF.md   ← S管理：作戦ブリーフ
│  ├─ portfolio-ledger.md ← S管理：採用/不採用/保留の台帳
│  ├─ _templates/         ← 各成果物の雛形
│  └─ EXP-OBSxxxxx/       ← 実験1件（OBS番号と一致）
│     ├─ 00-prescreen.md  ← S：目利きゲート
│     ├─ 00-spec.md       ← A：実験仕様
│     ├─ 10-result/       ← B：生データのみ
│     ├─ 20-review.md     ← C：採用/不採用判定
│     └─ 30-decision.md   ← D/E：反映 or 棚卸し記録
├─ obs/trading_app/       ← 既存：記録の「正」（件名ライフサイクル・方針・引き継ぎ）
├─ scripts/               ← 既存：検証スクリプト（Bが追記）
└─ src/                   ← 既存：本番実装（Dだけが触る）
```

- **`research/` は作業場（揮発）、`obs/` は記録の正（永続）**。結論が出たらEが要約をOBSへ吸い上げ、`research/EXP-*` は破棄してよい。二重管理の矛盾を防ぐ。
- `10-result/` には**生データのみ**を置く（Bは解釈しない）。Cが原データから独立に再判定できることが偽陽性の防波堤。

## 4. バケツリレー・フロー

1. **司令塔** がテーマを投入。
2. **S** が `00-prescreen.md` で目利き（GO/却下）。筋の悪い案は入口で却下。並行して **E** がOBS採番・起票。
3. **A** が `00-spec.md` を作成（成功基準を回す前に数値確定、選定/確認プロトコル、予測単位＋パイプライン両測定を指定）。
4. **B** が `scripts/` に実装、`10-result/` へ生データを出力（解釈しない）。
5. **C** が `20-review.md` でチェックリストを1項目ずつ検証し【採用可/不採用/保留】を宣告。
6. 分岐：
   - **不採用** → **E** が負の結果としてPJ000001変更履歴に学びを記録、OBSを90解決済へ。`EXP-*`破棄可。
   - **保留**（specの基準は満たすが本番投入の是非が追加投資・資本効率等の技術検証外の要因に依存する場合）→ **E** がOBSを`01開発アイデア`に留め置き（or `02対応検討中`へ）、判断材料をPJ000001変更履歴・`portfolio-ledger.md`に記録。**S**が次の一手として司令塔に判断材料を提示する。`EXP-*`は司令塔判断まで保持。
   - **採用可** → ここで **司令塔が最終GO** → **D** が `src/` へ統合・デプロイ・本番確認 → `30-decision.md`。
7. **E** がOBSライフサイクル移動＋リンク修正、引き継ぎ書・`ACTIVE.md` 更新。
8. **S** が `portfolio-ledger.md`・`STRATEGY-BRIEF.md` を更新し、次の一手を司令塔へ具申（ループを閉じる）。

### 4.1 運営の鉄則
1. **後戻り可**：前工程の成果物が揃わない限り次工程に進まない。specが曖昧ならAへ、データ不足ならBへ差し戻す。
2. **採用ゲートは人間**：Cの「採用可」は推薦。`src/`（本番）への統合＝Dの起動は必ず司令塔のGOを挟む。自動で本番反映しない。
3. **不採用こそ資産**：不採用もEが必ず方針の変更履歴に「なぜ不採用か」を残す。負の結果の蓄積が最大の防御力。
4. **B（実装）とC（判定）は必ず別エージェント**：自分の実装を甘く採点させない。

## 5. 司令塔（ユーザー）の関与ポイント
オペレーション極小の原則により、司令塔の必須アクションは次の2点に集約する：
- **入口**：Sにテーマを渡す（「〜を改善したい」）。
- **出口**：Cの採用/不採用の宣告に対し、本番反映の最終GOを出す。

状況把握はスマホから `research/ACTIVE.md`（進行状況）と `research/STRATEGY-BRIEF.md`（戦略的現在地）の2枚を見れば足りるようにする。
