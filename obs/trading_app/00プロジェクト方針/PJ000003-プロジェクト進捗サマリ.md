## 4. 重要課題と懸念点

### 4-1. 最重要課題（ブロッキング）

**① F2データの Binance ジオブロック問題（継続注意・非即時ブロッキング）**
- GitHub Actions（米国IP）は Binance Futures API が 451 でブロック → F2ペアが自動蓄積されない
- スクリプト側は graceful skip 実装済み（スクリプト自体は成功する）
- **暫定対策**: PC（非US IP）でのスクリプト手動実行時にBinanceデータが増分マージされる
- **根本対策（day90前に検討）**: A設計チームに参照取引所を OKX 等に変更するかSpec変更を依頼
- **非即時ブロッキング理由**: F2判定は day90 時点のC正式監査。それまでは中間チェックポイントのみ

### 4-2. 非ブロッキング申し送り

| 優先度 | 内容 |
|---|---|
| 中 | 破損JSON時の履歴喪失対策（.bak退避推奨） |
| 中 | btc-carry-executor: 初回LIVEポジション生成後、`margin_ratio_pct`の実データを見てwarn閾値(現85%)を早期側(例50-60%)に再調整すべきか判断（⑦フォロー） |
| 中 | btc-carry-executor: 初回LIVEオープン後、`leverage_set`ログとBitget実ポジション画面で実効レバレッジ(暫定5倍)を目視確認（⑧フォロー） |
| 低 | C-4: append復元prevSignalがpos（SMA=0測度ゼロでのみ問題） |
| 低 | 89日以内の実行継続（Bitget90日制限のため） |

### 4-3. 本番反映前の確認論点（技術的範囲外）

1. **スリーブ高Sharpe4.13の実取引可能性**: キャリーの平時ペニー拾い＋稀テールプロファイルがBitget実fundingで再現するか
2. **証拠金累積の楽観側仮定**: 清算頻度がやや過小評価（w*はCVaR駆動で採否頑健、フォワードF3で確認）
3. **mark価格問題**: バックテストはlast代用（保守側）、フォワードではmark実取得済み
