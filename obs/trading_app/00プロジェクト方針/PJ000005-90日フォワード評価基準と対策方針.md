## 1. 90日到達時（2026-10-02）の評価項目と合否基準

### 1-0. 試験値 → 本採否の切り替わり（いつ「判定」になるか）
- **Day89まで**: F1〜F4はすべて**試験値（interim）**。`forward-interim-metrics.json` に実測値と閾値の真偽値のみ出力（B実装官は判定語を使わない）。**この期間のゲート通過/未通過は採否を意味しない**。Day6時点でF1a+4.02/+7.62bpsが正でも「採用見込み」ではなく、単に較正が異常なく進行している信号にすぎない。
- **Day90到達（ライブ≥90暦日・2026-10-02見込み）**: `bitget-carry-forward-paper.ts` が `forward-f1f4-verdict-inputs.json`（F1〜F4最終実測値＋各閾値＋真偽値・両銘柄）を出力 → **C品質チームの較正監査（正式）を起動**。ここで初めて試験値が本採否の入力に切り替わる。
- **切替の鉄則**: Day90の実測がわずかに閾値未達でも、基準（calm片側90%下側境界・符号80%・清算0・T1 basisΔstd）を**後付けで緩めない**。未達は§2の判定フローに従い、C監査→司令塔上申で処理する。

### 1-1. F1〜F4 正式判定基準（spec §4・事前登録・変更不可）

評価対象 = **`phase=live` の連続≥90暦日**（warmup back-fill 30日は除外）。**BTC・ETH両方で成立して初めてF成立**（片銘柄のみは「単一資産の偶然」として不成立）。

|---|---|---|

| **F1b** 水準整合 | ライブ日次平均ネットキャリー(bps) **≥ calm窓 block-bootstrap 第10パーセンタイル下側境界** | calm日次平均: BTC **11.62** / ETH **14.40** bps。block-bootstrap（ブロック長7・N=5000・seed=20260705）でライブ同日数窓平均の分布→第10%ile。**未達は自動不採用にせず司令塔上申**（レジーム差の可能性・§1-2）。参考併記: FULL期間日次平均 BTC 1.586 / ETH 2.368 bps（ゲートではない） |

### 1-2. F1b未達の特別扱い（レジーム差 vs モデル欠陥の切り分け）
- calm窓（2021H1・高funding基準）は**構造的に高funding期間の参照値**。ライブ期間のfunding水準がcalmより低いレジームであれば、F1bはモデル欠陥でなく**レジーム差**で未達しうる。
- 判定順序: (i) **F1a（累積>0）が成立しているか** → 成立していればキャリー自体は実現している。(ii) F1b未達の場合、ライブ期間の実測funding水準を calm/FULL/T1 と対比し、**「calm対比で構造的に低fundingレジームだったか」をC監査が診断**。(iii) レジーム差起因なら**自動不採用にせず司令塔上申**（フォワード延長 or 縮小採用 or 不採用の人間判断）。
- **禁止**: F1b未達を回避するために閾値をFULL（1.586/2.368bps）に事後差し替えること。FULLはあくまで文脈提供の併記であり、ゲートはcalm片側90%下側境界で固定。

### 1-3. F2 Binance地理ブロック問題の扱い（nullの場合どう判断するか）

**問題**: リモート実行環境のIPをBinanceが451（Unavailable For Legal Reasons）でブロックし、`eventSignAgreementPct = null`。F1/F3/F4は正常だがF2の正式判定入力が取れない（既知・未解決）。

**扱いの原則（事前確定・HARKing防止）**:

F2は「BinanceでBitgetを代理できるという二段構え前提の較正」であり、他ゲート（F1実現キャリー・F3清算・F4 basis）は**Bitget実データのみで完結**する。F2 nullは、**Bitget実運用の生死そのものは既にF1/F3/F4で測れている**という構造を踏まえて扱う。

Day90到達時にF2がnullのままの場合の判定分岐:

| ケース | F2の状態 | 判定上の扱い |
|---|---|---|
| **A. F2復旧・母集団≥100ペア・両銘柄≥80%** | 有効な正式判定 | F2成立。F1/F3/F4と合わせ総合判定 |
| **B. F2復旧・母集団≥100ペア・一致率<80%** | 有効な正式判定・未達 | F2未達。§2判定フローで処理（本番前提未成立→上申） |
| **C. F2 null または 母集団<100ペア（地理ブロック継続）** | **判定不能（欠測）** | **F2を「代替手段で補完 or 判定保留」とし、F1/F3/F4の3ゲートで一次判定**。F2は「不成立の証拠なし」＝Stage0 G0-2と同じ「弱代表だが不成立の証拠でもない」状態を維持。**F2欠測を理由に自動不採用にしない／F2欠測を理由に自動採用にもしない**。司令塔上申事項（§5）とし、**F2代替検証の実施可否**を人間判断する |

**ケースCでのF2代替検証案（Day90前に実施を推奨・A/B/司令塔判断）**:
1. **代替データ源**: Bybit / OKX 等、地理ブロックを受けない取引所のperp fundingをBitgetとペア化し、**「Bitget funding が主要取引所群と符号整合するか」**を測る（Binance固有でなく「取引所間代表性」の一般化検証）。※これはF2の閾値80%を代替源へ流用する設計変更を含むため、**A設計チームが代替判定基準を事前登録**してから実施（HARKing防止・§6申し送り）。
2. **VPN/ローカル実行**: 地理ブロックを受けない環境で `bitget-carry-forward-paper.ts` のBinance取得部のみを定期実行し、F2母集団を別途蓄積。実装・運用はB/司令塔（環境）判断。
3. **F2判定保留での縮小採用**: F1/F3/F4が両銘柄成立し、かつF2が判定不能の場合、**「取引所代表性のみ未確認」という限定的リスクを明示した上での条件付き採用（縮小サイズ）**を選択肢とする。司令塔が代表性リスクを了承の上で判断（§2-2の「条件付き採用」に該当）。

**⚠ 原則**: F2 nullは**技術的欠測であって戦略の失敗ではない**。F2を「取れないから不採用」と扱うのも「取れないから無視して採用」と扱うのも誤り。Bitget単独で完結するF1/F3/F4を一次ゲートとし、F2は代表性の追加保証（取れれば強化・取れなければ限定リスクとして明示）と位置づける。

## 2. 定量的な採否判定フロー

> Day90（2026-10-02）にC品質チームが `forward-f1f4-verdict-inputs.json` を受けて実行する。**Cの宣告は推薦であり、本番反映は司令塔の最終GOを必須とする（PJ000002鉄則）。**

### 2-1. 一次分岐（F1/F3/F4 = Bitget単独完結ゲート）

```
【STEP 1】F3（清算・追証0件・両銘柄）は成立しているか？
  ├─ NO → 【不採用 or 要サイジング見直し】§3-1へ（テールバッファ不足の実証＝最優先の生死ゲート）
  └─ YES → STEP 2

【STEP 2】F1a（ライブ累積>0・両銘柄）は成立しているか？
  ├─ NO → 【不採用】キャリーが実データで純プラスに残らない（本テーマの中核仮説の棄却）
  └─ YES → STEP 3

【STEP 3】F4（basis日次変化std ≤ T1・両銘柄）は成立しているか？
  ├─ NO → 【条件付き / 上申】Bitget固有のbasis暴れがバックテスト最悪テール想定を平時に超過。
  │        w*再検討 or 縮小採用の司令塔上申（§3-4）
  └─ YES → STEP 4

【STEP 4】F1b（日次平均 ≥ calm片側90%下側境界・両銘柄）は成立しているか？
  ├─ NO → §1-2でレジーム差か診断
  │        ├─ レジーム差起因 → 【上申】フォワード延長 / 縮小採用 / 不採用の司令塔判断
  │        └─ モデル欠陥起因 → 【不採用】水準が構造的に想定を下回る
  └─ YES → STEP 5

【STEP 5】F2（符号一致≥80%・両銘柄）の状態は？
  ├─ 成立 → 【採用推薦】F1〜F4全成立（本番採用の前提成立）
  ├─ 未達（有効判定） → 【条件付き / 上申】取引所代表性が実測で不足（§2-2）
  └─ 判定不能（null・§1-3ケースC） → 【条件付き採用候補】F1/F3/F4全成立＋F2判定保留
                                     → 代表性リスク明示の縮小採用を司令塔上申（§2-2）
```

### 2-2. 三分類の定義

| 分類 | 成立条件 | 帰結 |
|---|---|---|
| **採用（推薦）** | F1a・F1b・F2・F3・F4 が**BTC・ETH両方で成立** | C較正監査で「採用可」を宣告 → **司令塔最終GO** → Dデプロイチームが本番反映。本番サイズはw*（BTC3.629/ETH3.789）フルまたは司令塔指定の段階導入 |
| **条件付き採用** | F1a・F3成立が前提。以下いずれか: (a) F1b未達だがレジーム差起因、(b) F4未達だが軽微超過、(c) F2判定不能（null）または未達 | C監査が「条件付き採用可（限定リスク明示）」を宣告 → 司令塔が**縮小サイズ導入 / フォワード延長 / 見送り**を判断。縮小サイズ = w*を割り引く（例: w*×0.5）or 初期資本500USDT据え置きでの小資本LIVE継続 |
| **不採用** | F3失敗（清算/追証発生・サイジング破綻）、または F1a失敗（累積が実データで負）、または F1b がモデル欠陥起因で未達 | C監査が「不採用」を宣告（司令塔GO不要）。**負の資産としてPJ000001変更履歴に記録**（偽陽性回避の資産）。②のスリーブ供給は他候補（OBS000033〜036）へ |

## 3. 結果パターン別の対策方針

### 3-0. 全ゲート通過 → LIVE移行（本格採用）の条件と手順

**条件（3点必須・PJ000002鉄則）**:
1. F1〜F4が**両銘柄で成立**（ライブ≥90日・§1-1）。F2は§1-3の扱いに従う。
2. **C品質チームの較正監査（正式）**で「採用可」宣告（`20-*` 判定書）。
3. **司令塔の最終GO**（本操作は司令塔の必須操作の一つ）。

**手順（Dデプロイチーム主管・戦略チームは関与しない）**:
1. 司令塔GO後、Dが本番統合。**段階的サイズ導入を推奨**（いきなりw*フルでなく、初期資本500USDT→段階増資でテール実挙動を実弾で確認しながら拡大）。
2. 本番反映後も**F3（清算/追証0）・F4（basis）の監視は継続**（本番ポジションに同じ早期警告を適用）。テールはフォワード90日で観測される保証がない（Bitget無料funding≈90日枯渇＝歴史的テール未到来の可能性）ため、本番後の初テール到来時が真の頑健性試験になる。
3. E進行チームがOBS000032を90解決済へ移動＋PJ000001/PJ000003更新。

**⚠ 戦略チームの警告（司令塔へ）**: バックテストSharpe4.13は「平時ペニー拾い＋稀テールで飛ぶ」プロファイル。フォワード90日で好成績でも、それは**平時キャリーの実現確認であってテール頑健性の証明ではない**。本格採用後も初期は小資本・段階増資で、初テールを実弾で通過するまで「採用済みだが観察中」の姿勢を保つこと。

### 3-1. F3失敗（清算/追証発生）→ 即時対応手順【最優先・90日を待たない】

清算・追証は本戦略の**生死ゲート**（サイジングが実運用で保守的に効いているかの直接検証）。発生時は90日到達を待たず即対応。

**即時対応（発生検知＝`liquidation_flag=1` または `margin_call_flag=1`）**:
1. **B/E**: `forward-alerts.log` 警告発火・`alert_active=true` を確認、`research/ACTIVE.md` に即時反映。司令塔へエスカレーション。
2. **層2（実弾）が既にLIVEの場合**: 該当ポジションを **`emergency-close.ts` で即時クローズ**（デルタニュートラル解消）。実弾の追証は実損失に直結するため、ペーパー層の分析を待たない。ドライラン中なら実損なし＝記録のみ。
3. **戦略チーム＋C**: 清算の原因分類:
   - **(a) 急騰による踏み上げ**（ショートperp証拠金枯渇）= Stage1で確認済みの「正当なモデル挙動」（ショートperpは暴落でなく急騰で清算）。想定内だがw*3倍・MMR0.5%バッファが実運用で不足した実証 → **w*見直し（縮小）or レバレッジ引き下げ**の要否をC/Aが検討。
   - **(b) funding反転タイミングのラグ損**（SMA7の反転遅延で証拠金枯渇）→ シグナル/ヒステリシス設計の課題（§4-1ヒステリシス帯の優先度上昇）。
   - **(c) データ欠損・会計バグ起因の誤検知** → B実装確認（偽の清算フラグでないか）。
4. **判定への帰結**: 清算・追証が1件でも発生 = F3失敗 = **§2フローで不採用 or 要サイジング見直し**。ただし原因が(a)想定内かつ被害が非破滅（現物益で相殺・再構築コスト24bpsのみ）なら、**w*縮小での再較正**を司令塔上申（自動不採用にせず、サイジングパラメータの実測較正として扱う選択肢）。

### 3-2. F1失敗（累積マイナス / キャリー持続マイナス）→ 対策
- **中間警告（早期）**: 累積ネットキャリーが負 かつ 直近10営業日連続で日次マイナス → `forward-alerts.log` 発火。
- **対策**: キャリー実現が構造的に負なら**本テーマの中核仮説（キャリーは純プラス）の棄却**に直結。ただしライブ短期のノイズと構造的負を切り分ける必要 → **Day90まで較正継続**（早期打ち切りは短期ノイズに過剰反応するリスク）。ただし清算連発を伴う持続マイナスは§3-1優先。
- **Day90でF1a負**: 不採用（§2 STEP2）。バックテストの好成績がBitget実データで再現しない＝Binance弱代表性の帰結。負の資産として記録。

### 3-3. F2失敗/欠測 → 対策
§1-3参照。復旧・代替検証・判定保留での縮小採用の3択。**F2単独失敗（F1/F3/F4は成立）を理由に全体を不採用にしない**（Bitget単独完結ゲートが成立していれば、代表性リスクは縮小サイズで管理可能）。

### 3-4. F4失敗（basis急拡大）→ ポジション縮小・停止の判断基準

**中間警告（早期）**: 直近30日のBitget basis日次変化std が T1水準（BTC12.14/ETH19.47bps）を超過 → `forward-alerts.log` 発火。

**段階的対応基準（basis暴れの度合いに応じる）**:

| basis日次変化std 水準 | 状態 | 対応 |
|---|---|---|
| ≤ calm水準（BTC5.08/ETH8.70bps） | 正常 | 通常運用 |
| calm超〜T1未満 | 注意 | 監視強化・記録。ポジション維持 |
| **T1超過（BTC12.14/ETH19.47bps）** | **F4逸脱** | **早期警告発火。層2実弾がLIVEなら新規サイズ増を停止（増資凍結）**。ペーパー層は較正継続（F4データ収集のため） |
| T1の1.5倍超（BTC≈18/ETH≈29bps）※本書で追加設定する運用停止目安 | 危険 | **層2実弾ポジションの縮小（w*×0.5へ）を司令塔上申**。basis単独暴発は現物ロング×perpショートの含み損拡大に直結 |
| T1の2倍超 or basis急拡大＋清算警告同時 | 緊急 | **`emergency-close.ts` で実弾ポジション即時クローズを推奨**。§3-1に合流 |

**⚠ 注記**: 上表の「T1×1.5」「T1×2」は**層2実弾（実損リスク）の運用停止目安**であり、**Day90のF4合否基準（T1固定）を緩めるものではない**。F4のゲート判定はあくまでspec §4のT1固定値で行う。運用停止目安は実損回避のための別軸（リスク管理）。この二軸を混同しないこと。

## 4. Day90後の改善実験ロードマップ

> **Day90までシグナル閾値・w*・全パラメータは凍結**（較正のクリーンさ保持・HARKing防止）。以下はDay90の正式判定後に、**別EXP（別OBS）として新規起票**して検証する仮説群。現時点では起票せず、本書に候補として記録する。

### 4-1. ヒステリシス帯の検証【第一候補・司令塔が直前セッションで合意済み】
- **仮説（起票時に1文で固定）**: signal_open_threshold_bps=0（現行・SMA7符号がゼロ跨ぎで即反転）を、**開帯 open≈5bps / 閉帯 close≈0〜2bps のヒステリシス**に変えると、ゼロ近傍でのfunding符号ノイズによる過剰反転（4レッグ往復コスト24bps/回の摩擦）を削減し、ネットキャリーが改善する。
- **狙う効果**: 反転回数の削減 → 反転コスト削減 → F1b水準整合の余裕拡大、かつ清算リスク（反転ラグ損=§3-1(b)）の低減。
- **リスク/対抗仮説**: 開帯を上げると「弱いが正のキャリー」を取り逃す（機会損失）。閾値グリッド探索はHARKingになる → **開帯/閉帯の値は理論・コスト分岐点（往復24bps ÷ 平均funding水準）から事前導出し、グリッド最良選択を禁止**。
- **検証設計（A設計チーム起票時）**: 較正で蓄積したライブ90日ledger＋Stage1バックテスト系列で、現行（threshold=0）vsヒステリシス版を**同一データで並走比較**。予測単位（反転回数・ネットキャリー）とパイプライン（清算・basis）両方で評価。Day90の凍結を破らないため、**必ずDay90判定確定後に着手**。
- **前提**: OBS000032が採用 or 条件付き採用された場合の改善策。不採用なら本項は棚上げ（テーマ自体が終了）。

### 4-2. その他の観察すべき改善ポイント（優先度順・Day90後に評価）
1. **w*の実測較正（フォワードデータでの再検証）**: Day90時点でF3清算が0件かつbasis/CVaRが想定内なら、w*3.629/3.789が保守的すぎないか（機会損失側）を検証。**⚠ フォワード90日ではテール未観測ゆえCVaR過小＝w*過大の罠（spec §0-3警告）**。w*引き上げは歴史的テールを含むデータでのみ再算出可。**フォワード単独でw*を上げてはならない**。
2. **MMR実値の確定**: 現行MMR0.5%は業界標準の仮置き（Bitget API非配信）。実運用LIVE後にBitget実際の維持証拠金率が判明したら、清算バッファ計算を実値で再検証。
3. **銘柄拡張**: BTC/ETH以外のBitget上場perp（SOL等）でキャリー・basis・清算プロファイルが成立するか。ブレッド拡張（IR≈IC×√ブレッド）に直結するが、銘柄ごとにテール較正が必要 → 別OBS。
4. **②配分層への統合（OBS000034合流点）**: 本スリーブが採用されれば、②マルチスリーブ・リスク配分層（OBS000034）にAが低相関スリーブを初供給する合流点が立つ。Day90採用後の本命ロードマップ。
5. **F2代替検証の恒久化**: Binance地理ブロックが継続するなら、Bybit/OKX等を含む「取引所間代表性」の恒久的モニタとして設計（§1-3案1の一般化）。

## 6. A設計チームへの申し送り事項（実装前の設計判断）

> 以下はDay90前後にA設計チームが仕様確定すべき論点。**回す前に数値で固定する**鉄則を守ること。

1. **F2代替判定基準の事前登録（J2が代替検証を選ぶ場合）**: Bybit/OKX等の代替funding源をペア化する場合、(i) 符号一致率の閾値（80%を代替源へ流用するか、代替源特性に応じ再設定するか）、(ii) 母集団最小ペア数（現行≥100想定）、(iii) 複数取引所の多数決 or 各取引所個別、を**代替検証を回す前に**spec化。結果を見て閾値を動かさない。
2. **ヒステリシス帯EXPの成功基準（§4-1）**: open/close帯の値を理論導出（往復コスト÷平均funding）で固定し、グリッド最良選択を禁止。現行threshold=0との比較の成功基準（反転回数削減率・ネットキャリー改善幅・清算件数）を回す前に数値化。**Day90凍結解除後に着手**。
3. **F4運用停止目安の位置づけ明確化（§3-4）**: 「T1×1.5」「T1×2」の運用停止目安は実損リスク管理の別軸であり、Day90のF4合否基準（T1固定）とは独立。specでこの二軸分離を明記し、運用停止目安をF4ゲート判定に混入させないこと。
4. **条件付き採用時の縮小サイズ算定式（J4）**: w×0.5等の割引を選ぶ場合、割引率の根拠（未確認ゲートの不確実性に対するサイジングペナルティ）を事前定義。市場確信での恣意的サイズにしない。
5. **本番採用後のテール監視設計（§3-0）**: フォワード90日で歴史的テールが未到来である前提を明記し、本番後の初テール到来時にw*・清算バッファの実挙動を検証する監視項目をspec化（採用=終了ではなく、初テール通過まで観察継続）。
